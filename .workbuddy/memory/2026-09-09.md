## JSON 参数处理 (HandleJsonParameter) 分析
- 背景: pg 系无 text→json/jsonb 隐式赋值转换, 参数必须显式 cast (::json/::jsonb) 或类型化参数。旧实现: `IDatabaseAdapter.HandleJsonParameter` + `ActionType`(Parameterized=改写 SQL 参数占位符加 ::JSON; ParameterValue=替换参数值为序列化 json), PostgreSQL/KingbaseES 各复制一份, 其余 provider 空实现。
- 发现的问题:
  1. Update 整列 Set(m=>m.Json, v) 路径 (UpdateBuilder.cs:323): Parameterized 分支依赖 ColumnValueMap 改写, 但 Update 传入 null → pg 实际 no-op, SET col=@p 无 cast, 疑似缺陷(待真库验证)。
  2. 批量插入 CreateInsertBatchSql (InsertBuilder.cs:92) 有 `TODO 批量插入对JSON列处理`, GenBatchInfos 未处理 JSON。
  3. 无 JsonHelper 时 ParameterValue 走 `"\"{value}\""` 裸引号包装, 仅对"值为 JSON 字符串"成立。
  4. 两个 Action 职责耦合(改 SQL + 改参数值), 依赖上下文 null 判断; 无自动化测试覆盖 insert/update/表达式三种 JSON 路径。
- 建议(方案A推荐): 新增 adapter 级"列值表达式"统一入口(默认 `@name`, pg 返回 `@name::jsonb`), Insert/Update/Batch/Upsert 全部走它, 删除 builder 内 IsJsonColumn 特判 + ActionType 双职; 参数值序列化拆成独立 hook。方案B(长期正解): 参数类型化 NpgsqlDbType.Jsonb, SQL 免 cast, 需核心参数层增强。方案C: 抽共享实现 + 修 update 整列 + 补测试。
- 涉及文件: Interfaces/IDatabaseAdapter.cs, Implements/CustomDatabaseAdapter.cs, Builder/InsertBuilder.cs, Builder/UpdateBuilder.cs, Models/JsonColumnContext.cs, Providers PostgreSQL/KingbaseES CustomAdapter。

## IDatabaseAdapter 拆分可行性分析(纯分析, 未改码)
- 设计模式: 拆独立接口 = 接口隔离原则 ISP(SOLID); 可选能力接口 + is 探测 = Role Interface / Capability interface, IDatabaseParameterBinder 是现有范例。
- 实证(各成员被 7 个 Provider 覆写数量): HandleInsertOrUpdate/HandleJsonColumn/HandleBatchInsert/Paging/HandleDateValue = 全 7/7(实为必备方言, 拆出无益); ReturnIdentitySql 4/7(Oracle/pg/Kingbase 用 RETURNING 不走它); FormatBooleanValue 2/7(pg/Kingbase TRUE/FALSE); HandleSelectGroupBySegment 1/7(仅 MySql), HandleMultipleQuerySql 1/7(仅 Oracle), DbCommandInit 1/7(仅 Oracle), FormatDateTimeValue 1/7(仅 Dameng), HandleBooleanValueForBulkCopy 1/7(仅 SqlServer); HandleBatchUpdate/Delete 0/7(全用基类 CASE WHEN 默认)。

## 修复: PostgreSQL/KingbaseES 批量插入 DateTime(Kind=Local) 报 Npgsql timestamptz 错误
- 现象: PostgreSQL.ExecutionTest.Repository_Async_Operations_Test 失败: "Cannot write DateTime with Kind=Local to PostgreSQL type 'timestamp with time zone', only UTC is supported."
- 根因(多层): ① LightORM 建表把 CLR DateTime 映射为 PG 无时区 `timestamp`(Utils/FormatType.cs: System.DateTime=>TIMESTAMP, DateTimeOffset=>TIMESTAMPTZ); ② 但参数兜底用 DbType.DateTime 绑定, Npgsql 把 DbType.DateTime 推断为 timestamptz, 拒绝 Kind=Local。③ 批量路径 InsertProvider.ExecuteAsync 用 BatchSqlInfo.ToDictionaryParameters() 产出的无列 Dictionary<string,object>, 经 BindDictionary 时 column=null, PG binder 只处理 json 返回 false, 落入 DbType.DateTime 兜底。单条/批量都被此问题影响(单条有 column 但 binder 未处理 DateTime)。
- 修复: 扩展 PostgreSQL CustomPostgreSQL.cs + KingbaseES CustomKingbaseESAdapter.cs 的 IDatabaseParameterBinder.BindParameter: `value is DateTime` 时显式设 NpgsqlDbType/KdbndpDbType.Timestamp(无时区), 按字面(墙上时间)写入, Local/Unspecified/Utc 均可。与建表列类型一致, 也使 PG 与其余 6 provider 的 naive datetime 语义一致。DateTimeOffset 保持默认(timestamptz, Npgsql 原生带偏移处理, 无需改)。
- 语义注记: 若第三方手建 timestamptz 列却映射为 DateTime? 属性, 旧行为(Utc 值)可绑但现在按无时区字面写, 可能时移; 契约上 timestamptz 应走 DateTimeOffset。框架自建表 DateTime→timestamp 无时区。
- 验证: PG + KingbaseES provider 均 0 错误编译(无法本地跑集成测试, 需真库)。

### 更正/深挖: DateTime 绑定失败的真正机制 (用户问是否与建表有关)
- 反编译 Npgsql 10.0.3 确认 NpgsqlDbTypeExtensions: `DbType.DateTime => Legacy ? Timestamp : TimestampTz` (非 legacy 时固化为 timestamptz)。反向: `TimestampTz => DbType.DateTime`, `Timestamp => DbType.DateTime2`。
- 官方规则: Npgsql 6+ 对【未设类型】的 DateTime 是 Kind 感知的: Utc→timestamptz, Local/Unspecified→timestamp(无时区, 可写); 但【显式设 DbType.DateTime】被固化映射为 timestamptz → 拒绝 Kind=Local。
- 结论: 真正触发失败的是 LightORM 统一绑定里 `p.DbType = DbType.DateTime`(DbParameterReader.GetDbTypeAndValue 兜底), 把 DateTime 强转为 timestamptz 语义。与"9/7 是否通过"取决于: 当时列实际类型 + 值 Kind + 是否走显式 DbType 路径。
- HEAD(9/8)/9/7 的 ReadDictionary(批量 Dictionary<string,object>) 同样设 DbType.DateTime → 理论上 Local 也应失败; 种子数据 InitDatas 从不写 LastLogin(恒 NULL), Repository_Async_Operations_Test 是首个真 DateTime 写入 → 疑 9/7 并未在同库同场景真正写入过 Local DateTime。
- 建表列类型是决定因素: 列 timestamp(无时区) + 显式 DbType.DateTime(=timestamptz) → Npgsql 客户端即抛 Local 不被支持; 若列本身 timestamptz 则应传 Utc。待用户确认 USER.LAST_LOGIN 实际类型(信息架构)后再定最终修法。

### 更正(用户澄清, 推翻上一条"列类型为决定因素"归因): 测试通过是因为 binder 代码, 与重建表无关
- 用户明确: "测试通过是因为你加的代码"。核实 DbParameterReader.CreateParameterValue(121-141): 所有建参路径(字典带列/裸字典/对象)都先 `if (adapter is IDatabaseParameterBinder binder && binder.BindParameter(...))`(133), binder return true 即接管、直接 return p; 只有 false 才落到 GetDbTypeAndValue → p.DbType=DbType.DateTime(Npgsql 固化 timestamptz) → Local 必拒。
- PG/Kingbase binder 新增的 `value is DateTime → NpgsqlDbType/KdbndpDbType.Timestamp` 分支接管并返回 true, 把 Local DateTime 固定为无时区写入 → 参数类型不再依赖列、更不依赖 DbType 兜底。因此**测试通过的关键是 binder 接管**, 表列是 TIMESTAMP 还是 TIMESTAMPTZ 根本不影响参数写入; 用户顺手重建表是无关联因, 被我误记为"决定因素"。此归因作废。

## DateTime binder 收敛: 方案 X(Kind 感知)已落地(用户选 X, 编译通过)
- 用户选方案 X。PG CustomPostgreSQL.cs + KingbaseES CustomKingbaseESAdapter.cs 的 BindParameter DateTime 分支由"一律 Timestamp"改为 Kind 感知三目:
  `dateTime.Kind == DateTimeKind.Utc ? (NpgsqlDbType/KdbndpDbType).TimestampTz : (NpgsqlDbType/KdbndpDbType).Timestamp`。
  Utc→timestamptz(保服务端时区语义), Local/Unspecified→无时区 timestamp(与自建 no-tz 列一致、墙上时间字面写)。
- 语义边界: Utc 值若落到自建 no-tz 列, 服务端会做会话时区转换(可能时移)——用户已知悉并接受; timestamptz 列应配 DateTimeOffset 属性才是干净契约。
- 验证: PG net8.0/net462、KingbaseES net8.0 均 0 错误(NpgsqlDbType.TimestampTz / KdbndpDbType.TimestampTz 枚举存在)。集成测试种子用 Local DateTime → 现在走 Timestamp 分支, 与重建表前行为一致仍通过。
