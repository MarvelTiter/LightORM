## 更正：上一段的"对齐 PG"说法有误

用户指出 **PG 不用 `JSON_VALUE` / `JSON_QUERY`**，核对代码后确认：

| 方言 | 读取路径实际写法 | 位置 |
|---|---|---|
| PG | 中间层 `->`（返回 json）/ **末级 `->>`（返回 text）** + 显式 `::<目标类型>` cast | `CustomPostgreSQL.cs:141-222` |
| Oracle | 无条件 `JSON_VALUE(col,'$.path')`，无 `JSON_QUERY` 分支 | `CustomOracleAdapter.cs:131`、`OracleMethodResolver.cs:204` |
| SqlServer | 读取走 `JSON_VALUE`（`CustomSqlServerAdapter.cs:121`） | — |

**`JSON_VALUE` / `JSON_QUERY` 是 Oracle 自己的函数对，不是 PG 的。** 框架里真正"按标量/复合分流"的地方是
**写路径**：SqlServer 复合值 `JSON_QUERY(@p)` 包装 / 标量传原生值（`CustomSqlServerAdapter.cs:84-172`），
Oracle 写路径同理（`JSON(:p)`）。PG 不需要这个分流，因为它末级一律 `->>` 取文本再 cast。

⇒ 修正后的说法：Oracle 读取路径可考虑**自身**引入 `JSON_QUERY`（21c 同样提供）做「标量 `JSON_VALUE` /
复合 `JSON_QUERY`」分流，并给 `JSON_VALUE` 加 `RETURNING CLOB` 解决截断；这与 PG 的实现无关，PG 只是
"末级取文本 + cast"这一思路的参照。

## 「Oracle 要不要做标量/复合分流」——分写/读两条路看

`HandleJsonColumn` 是**读、写共用**的入口（唯一调用点 `ExpressionResolver.cs:541`），按 `Options.SqlType` 分流：

| 路径 | Oracle | SqlServer | 结论 |
|---|---|---|---|
| **写**（Update + 路径/整列） | `JSON(:p)` 统一解析，**无形状分流** | 复合 `JSON_QUERY(@p)` / 标量传原生值（`JSON_MODIFY` 的要求） | **Oracle 不需要分流**，21c XE 实测通过即证明 |
| **读**（Select/Where 成员访问） | 裸 `JSON_VALUE(col,'$.path')` | 裸 `JSON_VALUE` | 两边都一样，**都没有分流** |

**关键判断**：Oracle 测试通过**不能**证明复合读取可用 —— 现有用例里 json 成员引用的**末级 100% 是标量**
（`SelectSql_Json.cs` 全是 `j.Json.NestJson.Name == "test"`、`j.JsonList[0].NestList[1].NestJson.NestList[2].Name`），
没有一例把**对象/数组本身**当末级取。裸引用整列（`select j.Json`）走 `Members.Count==0` 分支 → 生成裸列名、
客户端反序列化，所以整列读也是好的。

⇒ 写路径：**不需要分流**，保持不动。
⇒ 读路径：**待验证的潜在缺口**，非"已通过"。触发条件是 `select/where` 里取**复合末级成员**
（如 `j.Json.NestJson`），Oracle/SqlServer 的 `JSON_VALUE` 对非标量返回 NULL。
验证方式：加一条取复合成员的用例实跑，而不是靠现有全绿推断。

## 验证与修复：读取路径的复合末级成员

### 一、先落用例，实跑复现（Oracle 21c XE）

新增 `ExecutionTest.JsonColumn_CompositeMember_Projection`。**第一版写错了形状**：直接
`ToListAsync(j => j.Data!.NestJson)`（目标类型就是 `JsonData`）会走 `CreateCustomEntiry`，
按"列名匹配"给 JsonData 找列 → reader 生成为 `new JsonData() {}`（空对象），
SQLite/Oracle 都失败。**框架支持的形状是匿名投影**（`new { N = j.Data.NestJson }`）：
`BuildFunc` 对匿名类型走 `CreateAnonymous`，成员类型命中 `ContainsJsonType`（json 列类型在建列时
经 `ColumnInfo.AddJsonTypeMap` 注册）后走 `GetTargetJsonExpression` → `RecordFieldStringDeserializer`。

用匿名投影复跑，Oracle 的 SQL 是 `JSON_VALUE(a0."DATA",'$.NestJson')` → 读回空 `JsonData`
（`JSON_VALUE` 对非标量返回 NULL）⇒ **缺口确认**。

### 二、修复（生成期按表达式结构分流）

新增 `JsonParameterHelper.IsCompositeJsonLeaf(JsonColumnContext)`，Oracle / SqlServer 的**读取分支**
据此在 `JSON_VALUE` / `JSON_QUERY` 之间选（写路径不动：Oracle 的 `JSON(:p)` 与 SqlServer 的
`JSON_MODIFY` 分流各自保留）。

判定口径（关键）：`JsonColumnContext.Members` 是 `Stack<MemberPathInfo>`，**枚举顺序 == Pop 顺序**，
最后一个元素 = json 路径最内层（末级）；末级 `Member == null`（纯索引路径 `Arr[1]`/`Lst[0]`）时
退回 `Column.ColumnType` 再取元素类型；`JsonNode/JsonObject` 之类索引器语义不可判定 → 按标量（保守，不变更既有语义）。

### 四、非匿名目标类型已支持（修正上面的"第一版写错了形状"）

**更正**：上文"框架支持的形状只有匿名投影"是当时的**框架缺陷**，不是设计意图。用户随后改了
`ExpressionBuilder.CreateCustomEntity`（顺手把拼写 `CreateCustomEntiry` 一并修正）：

```csharp
Expression CreateCustomEntity(Type targetType)
{
    if (ContainsJsonType(targetType))
        return GetTargetJsonExpression(reader, Culture, recordInstanceExp, SchemaTable, 0, targetType);
    var columns = TableContext.GetTableInfo(targetType).Columns;   // 原逻辑
    ...
}
```

- 依据：`ToListAsync(j => j.Data!.NestJson)` 这类投影 SQL 只 SELECT **一列**，所以第 0 列就是该 json
  表达式，按 `targetType` 反序列化即正确（`GetJsonDeserializeExpression` 本来就按 `TargetType` 走
  `StringDeserializer`/`BytesDeserializer`，与是否匿名无关）。
- `ContainsJsonType(t) => JsonMaps.ContainsKey(t)`，而 `JsonMaps` 只在 `[LightJsonMap]` 属性建列时经
  `ColumnInfo.AddJsonTypeMap` 注册 → **实体类型不在表里**，所以不会误伤普通实体映射；`CreateAnonymous`
  内嵌调用 `CreateCustomEntity` 的那条路（成员非 json）也不会命中新分支。
- 用例 `JsonColumn_CompositeMember_Projection` 现在**两种形状都留着**（匿名 `new { N = j.Data!.NestJson }`
   + 非匿名 `j.Data!.NestJson`），用户实测 Oracle 通过，2026-09-17 复核 SQLite 通过。
