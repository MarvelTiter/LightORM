## 更正：上一段的"对齐 PG"说法有误

用户指出 **PG 不用 `JSON_VALUE` / `JSON_QUERY`**，核对代码后确认：

| 方言 | 读取路径实际写法 | 位置 |
|---|---|---|
| PG | 中间层 `->`（返回 json）/ **末级 `->>`（返回 text）** + 显式 `::<目标类型>` cast | `CustomPostgreSQL.cs:141-222` |
| Oracle | 无条件 `JSON_VALUE(col,'$.path')`，无 `JSON_QUERY` 分支 | `CustomOracleAdapter.cs:131`、`OracleMethodResolver.cs:204` |
| SqlServer | 读取走 `JSON_VALUE`（`CustomSqlServerAdapter.cs:121`） | — |

**`JSON_VALUE` / `JSON_QUERY` 是 Oracle 自己的函数对，不是 PG 的。** 框架里真正"按标量/复合分流"的地方是
**写路径**：SqlServer 复合值 `JSON_QUERY(@p)` 包装 / 标量传原生值（`CustomSqlServerAdapter.cs:84-172`），
Oracle 写路径同理（`JSON(:p)`）。PG 不需要这个分流，因为它末级一律 `->>` 取文本再 cast。

⇒ 修正后的说法：Oracle 读取路径可考虑**自身**引入 `JSON_QUERY`（21c 同样提供）做「标量 `JSON_VALUE` /
复合 `JSON_QUERY`」分流，并给 `JSON_VALUE` 加 `RETURNING CLOB` 解决截断；这与 PG 的实现无关，PG 只是
"末级取文本 + cast"这一思路的参照。

## 「Oracle 要不要做标量/复合分流」——分写/读两条路看

`HandleJsonColumn` 是**读、写共用**的入口（唯一调用点 `ExpressionResolver.cs:541`），按 `Options.SqlType` 分流：

| 路径 | Oracle | SqlServer | 结论 |
|---|---|---|---|
| **写**（Update + 路径/整列） | `JSON(:p)` 统一解析，**无形状分流** | 复合 `JSON_QUERY(@p)` / 标量传原生值（`JSON_MODIFY` 的要求） | **Oracle 不需要分流**，21c XE 实测通过即证明 |
| **读**（Select/Where 成员访问） | 裸 `JSON_VALUE(col,'$.path')` | 裸 `JSON_VALUE` | 两边都一样，**都没有分流** |

**关键判断**：Oracle 测试通过**不能**证明复合读取可用 —— 现有用例里 json 成员引用的**末级 100% 是标量**
（`SelectSql_Json.cs` 全是 `j.Json.NestJson.Name == "test"`、`j.JsonList[0].NestList[1].NestJson.NestList[2].Name`），
没有一例把**对象/数组本身**当末级取。裸引用整列（`select j.Json`）走 `Members.Count==0` 分支 → 生成裸列名、
客户端反序列化，所以整列读也是好的。

⇒ 写路径：**不需要分流**，保持不动。
⇒ 读路径：**待验证的潜在缺口**，非"已通过"。触发条件是 `select/where` 里取**复合末级成员**
（如 `j.Json.NestJson`），Oracle/SqlServer 的 `JSON_VALUE` 对非标量返回 NULL。
验证方式：加一条取复合成员的用例实跑，而不是靠现有全绿推断。

## 验证与修复：读取路径的复合末级成员

## 达梦测试为什么明显慢（14:00 排查，全用探针实测）

结论：**慢的不是查询、也不是驱动，而是「每个用例都重建整个 schema」× 「达梦 DDL 特别贵」× 「达梦项目把共享套件跑了两遍」。**

### 逐项实测（探针跑完即删）

| 阶段 | Dameng | KingbaseES | 倍数 |
|---|---|---|---|
| 10 × DROP TABLE | 660 ms | 306 ms | 2.2× |
| **10 × CREATE TABLE（含 COMMENT/INDEX）** | **3899 ms** | **187 ms** | **20.8×** |
| 8 × FullDelete | 116 ms | 49 ms | 2.4× |
| Insert 6 行 | 83 ms | 30 ms | 2.8× |
| 合计（=`[TestInitialize]` 单次） | **≈4.8 s** | **≈0.57 s** | 8.4× |
| SQLite 同项对照 | — | SQLite **≈13 s**（最慢） | — |

- **查询与驱动都很快**：`Select_Single_Column` 里 6 条 SQL 的驱动耗时只有 1.7–6.9 ms，整方法却耗时 33 s；
  LightORM 完整查询 10 ms/次、生成 SQL 0–1 ms/次；裸 Dm 建连 3–5 ms（仅首次 `Server=localhost` 有 108 ms DNS）。
- **元凶是 `[TestInitialize]`**（`test/LightORMTest/ResultTest/ExecutionTest.InitData.cs:32`）：每个测试方法前
  10 张表 DROP + 重建 + 8 张表 FullDelete + 重插种子数据。MSTest 的用例耗时包含 TestInitialize，所以
  每个用例都有 ≈4–5 s 的底噪；`Ado_Executor_Methods_Test` 39 s、json 批处理 36 s 等则是在此之上再叠加。
- **建表语句条数结构差异（框架侧可优化点）**：
  - `DamengTableHandler.Writer`：`CREATE TABLE` / 每条 `COMMENT ON COLUMN` / 每条 `CREATE INDEX` **各 yield 一次**
    → 10 张表共 **131 条语句 = 131 次往返**（实测：CREATE TABLE 10 + COMMENT 76 + INDEX 45）。
  - `KingbaseESTableHandler.Writer` / PostgreSQL：把它们 `AppendLine` 到同一个 `StringBuilder`，**每表 `yield` 一次**
    → 10 张表 ≈10 次往返（Npgsql/Kingbase 支持一次命令多语句）。
- **达梦服务端 DDL 本身也贵**：裸 DmConnection 直接 `DROP TABLE` 10 张 = **2205 ms（≈220 ms/张）**，与 LightORM 无关。
- **用例数差异**：`dotnet test --list-tests` 实测 Dameng **270** / KingbaseES 100 / Oracle 194 / Sqlite 168。
  达梦多出来的部分来自① `test/LightORMTest.Dameng/SelectResult.cs` 与 `ResultTest/ExecutionTest.cs` **都继承了共享
  `ExecutionTest`（100 个用例）→ 整套跑两遍**（PostgreSQL / SqlServer 也有同样的重复类）；② 额外的
  AdoTest / BulkCopyTest / CreateTableTest / DbMethodTest / RepositoryTest 等继承类。
- 270 个用例 × ≈5 s 底噪 ≈ 22 min，实测 11.5 min 只跑完 54 个（含 36–39 s 的重用例），与观察一致。

3. 删掉 Dameng/PostgreSQL/SqlServer 里重复的 `SelectResult` 类（用例数直接减半）。

### 达梦 DDL 慢的定量归因（探针实测，2026-09-17 下午）
用裸 `DmConnection`（不经 LightORM）跑 8 张表 × [1 建表 + 10 条 `COMMENT ON COLUMN` + 4 条 `CREATE INDEX`] = 120 条语句：
- **逐条执行合计 3412ms**；明细 `CREATE 205ms(25.6ms/条)` / `COMMENT 2022ms(25.28ms/条)` / `INDEX 788ms(24.63ms/条)`
  ⇒ **每条 DDL 恒定 ~25ms，与语句内容无关**（置一条注释和建一个索引一样贵）⇒ 是 DM 的"每条 DDL 自带一次提交/落盘"的固有代价，不是语句复杂度。
- **DM 不接受 `;` 分隔的多语句命令**：合并成 8 个命令直接 `DmException: 第 2 行…[COMMENT]附近出现错误: 语法分析出错`。
- **Oracle 风格匿名块 `BEGIN EXECUTE IMMEDIATE '…'; … END;` 反而更慢**：同样 120 条语句合并为 8 个命令 = **23397ms（≈2.9s/块，比逐条慢 ~7 倍）**，语法上能过但不可用。
  ⇒ 结论：达梦这条路的**批量化救不回来**，唯一可控手段是**减少 DDL 语句条数/次数**。
- 与框架层测量自洽：`DamengTableHandler.Writer` 对 `CREATE TABLE` / 每条 COMMENT / 每条 INDEX 各 `yield` 一次，而 `InternalCreateTableAsync` 是 `foreach (var s in sqls) await ado.ExecuteNonQueryAsync(s)` → 一次 yield = 一次往返。10 张表 131 条 ≈ 141 条 × 25ms ≈ 3.5s，正是单次 init 4.8s 的大头。
  对照 `PostgreSQLTableHandler.Writer`：把同表的 CREATE/COMMENT/INDEX 全 `AppendLine` 进一个 `StringBuilder`，**每表只 yield 一次**（约 10 次往返）→ 187ms。
- 测试侧另有放大器：`LightORMTest.Dameng/SelectResult.cs` 与 `ResultTest/ExecutionTest.cs` **都继承共享 `ExecutionTest`（100 用例）** → 达梦项目发现 270 个用例（Oracle 194 / Sqlite 168 / KingbaseES 100）。

- 同一 DbBaseType 存在多个 adapter 实例：`ExpressionSqlOptions.customDatabases` 只留第一个注册的；provider 自己另有一个；MySQL 还有 `CustomMySqlAdapter.Instance`。
- 离线场景：`test/**/SqlGenerate/*` 用例只 `Console.WriteLine`，**不连库**；且 `ToSql()` 是公开 API，本就要求无连接可用。

**时机结论（关键）**
- `InsertProvider.Execute()` → `sqlBuilder.ToSqlString(Database)` → `ado.ExecuteNonQueryAsync(sql,...)`：**SQL 在连接打开前就定稿**。`ToSql()` 更是完全无连接。
- ⇒ 任何"从业务连接读 `DbConnection.ServerVersion`"的方案（含挂在 `conn.Open()` 上）只能保证"后续语句"，首语句与纯生成场景必然错档 → **已废弃**。
- 修正设计：探测与业务连接**解耦**。触发点 = 方言第一次**真正读取某个能力位**时（SQL 构建期）；通道 = 独立短超时连接 `Open()` 一次（`ServerVersion` 无需发查询）；结果按 (方言, 连接串) 缓存 + Single-flight；失败**不抛**，退保守基线并负缓存。
- 另一条要点：能力读取必须**下沉到具体分支内部**（如 MySQL 只在 `IsRollup/IsCube/GroupingSets` 为真时才求值），否则每次 select 都会触发探测。这样普通 CRUD 零探测成本。
- 基线档取向改为**保守**（正确性优先）：SqlServer → 旧式 ROW_NUMBER 分页、`LTRIM(RTRIM())`；MySQL → `WITH ROLLUP`。探测成功即升级为精确档；无库/无权限/`ServerVersion` 未实现时只损失新语法，不产生非法 SQL。
- 新增能力不必改 `IDatabaseAdapter`（会破坏第三方实现）：复用已有 `Builder/AdapterCapability.TryGet<T>` 穿透 `ScopedDatabaseAdapter` 探能力接口。
- 模型建议：`[Flags] DbFeatures` + `DbCapabilityProfile(Vendor, Version, Features, Source=Explicit|Probed|Assumed, Signature)`；`IDbVersionDetector.Detect(DbConnection)` 每方言一个。MariaDB 10.x 版本号不能直接与 MySQL 8.0 比较，须先判厂商。
- 待实测：各方言 `DbConnection.ServerVersion` 是否可用/格式/异常（重点 Dameng 的 `DmConnection` 可能 `NotImplementedException`、net462 的 `System.Data.SqlClient`、KingbaseES 版本串解析）。

## 【根因修正】缓存键的第一维度是"标识符引用身份"，不是版本能力（用户指正）
我此前把 P0 定性为"版本维度缺失"，**不准确**。实际：
- **标识符引用在解析期就写进了结果**：`ExpressionResolver` 358/425/430/474/565 行 `Sql.AppendEmphasis(col.ColumnName, Database)`；`AppendEmphasis`（`Extension/CustomDatabaseExtensions.cs:65`）读 `database.Emphasis` 与 `database.QuoteIdentifiers ?? database.UseIdentifierQuote`（关键词命中时强制加引用）。⇒ `ExpressionResolvedResult.SqlString` 自带 `[Col]` / `` `Col` `` / `"Col"`。
- **参数前缀不在解析结果里**（用户指出，正确）：解析期只用 `ResolveContext.ParameterPrefix`；`database.Prefix`（`@`/`?`/`:`）在下游 `SqlBuilder.HandleSqlParameters` 经 `database.AttachPrefix()` 补上（SqlBuilder.cs:82/90）⇒ 前缀不构成缓存维度。
- **缓存无任何清理入口**：`expressionResolvedResultCache` 全仓库只有 `TryGetValue`/`TryAdd`，没有 `Clear`。
- ⇒ **这是既存缺陷、与版本探测无关**：同进程两个方言（或同方言不同 `QuoteIdentifiers`）解析同一表达式，第二次会命中第一次的引用符号。
- **正确的缓存键模型**：`(SqlAction, 标识符引用身份, Hash, Depth)`，其中"引用身份"至少含：`Emphasis` + 生效引用开关（`QuoteIdentifiers ?? UseIdentifierQuote`）+ 关键词集（命中即强制引用，故也算维度）+ provider 私有的版本身份（可选接口叠加，核心不解释）。
- 注意 `QuoteIdentifiers` 是**每条语句**经 `ScopedDatabaseAdapter(database, quote)` 生效的，故该维度必须按"当次生效值"取，不能只看 adapter 实例。

## 【实测】方言隔离 A/B 跑通 + "只加 Emphasis 够不够"的反例（16:0x）

### 先说一个此前踩的坑：多 provider A/B 的 harness 必须用不同 key
`ExpressionSqlOptions` 的 `databaseProviders` / `customDatabases` / `databaseHandlers` / `defaultDbKey`
**全是 static 全局**，而 `SetDatabase` 对同名 key 走 `TryAdd` → **先注册者胜、后来者被静默丢弃**。
默认 key 是 `"MainDb"`（`ConstString.Main`），所以连续两次 `UseSqlServer(...)` / `UseMySql(...)`
（都走无 key 重载）时**只有第一个生效**，第二个 context 实际仍在用第一个方言的适配器 ——
我最初那次 A/B 里 MySql 输出了 `[PRODUCTS]` 就是这个原因，**不是缓存污染**。

正确做法：`UseSqlServer("SS", ...)` / `UseMySql("MY", ...)` 用**具名 key** 注册，
再用 `IExpressionContextSetup.SetDefault("SS"|"MY")` 切换（该方法也是全局的，但顺序调用即可）→
同一进程、同一静态缓存里就能做真正的 A/B。

### DEMO 3：跨方言隔离（修复后的正确行为）
固定一条表达式，SS → MY → ORA 轮换解析，各自拿到正确的引用符号，且切回 SS 仍是 `[bracket]`：
```
SS : SELECT a0.[PRODUCT_ID] ... FROM [PRODUCTS] a0 WHERE (a0.[PRODUCT_CODE] = 'xyz')
MY : SELECT a0.`PRODUCT_ID` ... FROM `PRODUCTS` a0 WHERE (a0.`PRODUCT_CODE` = 'xyz')
ORA: SELECT a0."PRODUCT_ID" ... FROM "PRODUCTS" a0 WHERE (a0."PRODUCT_CODE" = 'xyz')
```
两方言各占一条缓存（`TryAdd` 先到先得，不覆盖），证明 `ResolveIdentity` 维度真的在起隔离作用。

### DEMO 1：**Emphasis 单独进键不够** —— 同 Emphasis、不同方言
| 方言 | `Emphasis` | `UseIdentifierQuote` 默认 | 解析输出 |
|---|---|---|---|
| Oracle | `""` | `true` | `a0."PRODUCT_NAME" AS "ProductName"` / `FROM "PRODUCTS" a0` |
| PostgreSQL | `""` | **`false`** | `a0.PRODUCT_NAME AS ProductName` / `FROM PRODUCTS a0` |

四个方言共用 `""`：Oracle / PostgreSQL / KingbaseES / Dameng
（`CustomOracleAdapter` / `CustomDamengAdapter.cs:15` / `CustomKingbaseESAdapter.cs:23`）。
它们现在恰好因为引用开关默认值不同而分开，一旦用户给 PG 打开引用（`UseIdentifierQuote(true)`）
或给 Oracle 关掉，Embed 相同 ⇒ **只按 Emphasis 进键就会撞同一条缓存**。

### DEMO 2：同方言、同 Emphasis，逐语句翻转开关，结果就变
`.QuoteIdentifiers()` / `.NoQuoteIdentifiers()` 经 `ScopedDatabaseAdapter` 覆盖当次生效值：
```
SS 默认              : a0.[PRODUCT_NAME] / FROM [PRODUCTS]
SS NoQuoteIdentifiers: a0.PRODUCT_NAME   / FROM PRODUCTS
SS 再默认            : a0.[PRODUCT_NAME] / FROM [PRODUCTS]
```
⇒ 引用开关（`QuoteIdentifiers ?? UseIdentifierQuote`）是**独立于 Emphasis 的第二维度**，必须进键。

### 结论：Emphasis 是主维度但**不充分**
`Combine` 的三件套都是必要的：
1. `Emphasis` —— 引用符号字面量（`[]` / `` `` `` / `""`），覆盖大多数方言差异；
2. 生效引用开关 —— 同 Emphasis 的方言（PG vs Oracle）与同方言逐语句切换都靠它区分；
3. provider 私有 `IDbResolveIdentity` —— 版本/能力相关分支（`TRIM()`、`ROLLUP()`、自增列 DDL 等）的兜底。

**仍未覆盖（诚实边界）**：`keyWorks` 关键词集。`CustomDatabaseAdapter.IsKeyWord` 读的是
**per-adapter 可变的** `HashSet`（`AddKeyWord` 可追加），引用关闭时命中关键词仍强制加引号。
默认关键词集未变时无影响；需要时由 provider 在自己的 `IDbResolveIdentity` 里并入 —— 这正是留的口子。
`Prefix` 确认**不是**维度（`AppendEmphasis` 完全不读它，前缀在 `SqlBuilder.HandleSqlParameters` 由 `AttachPrefix` 补）。

## 【追问】"身份 == Emphasis 就够了吗" —— 单方言隔离矩阵实测（16:3x）

用户追问：**Emphasis 相同 ⇒ 解析结果可复用？"实际上有没有用到 Emphasis"有关系吗？**
结论：**不成立，而且与"有没有用到 Emphasis"无关** —— 解析期从 adapter 读的东西不止引用符号。

### 关键：单方言独立进程取真值（多方言同进程会被污染，不可信）
探针 `%TEMP%\dbver-probe`，每次进程只注册**一个**方言（`dotnet run -- <key>`）：

| 运行时 key | Emphasis | 引用开关 | bool 字面量 | 标识符 |
|---|---|---|---|---|
| Oracle | `""` | true | **`1`** | `"ACCOUNTS"` / `"NICKNAME"` |
| Oracle-quote | `""` | true | `1` | 同上 |
| **PostgreSQL-quote** | **`""`** | **true** | **`TRUE`** | `"ACCOUNTS"` / `"NICKNAME"` |
| PostgreSQL | `""` | false | `TRUE` | 裸 |
| SqlServer V1 / Over2017 | `[]` | true | `1` | `[ACCOUNTS]` |

⇒ **Oracle 与 PG(引用显式打开)：Emphasis 相同（`""`）、引用开关相同（true），bool 字面量一个是 `1` 一个是 `TRUE`。**
差异来自 `FormatBooleanValue`（PG/KES 覆写返回 `TRUE`/`FALSE`，其余基类 `1`/`0`），
由 `ExpressionResolver:670/675 → Database.HandleBooleanValue` **在解析期写进 `SqlString`**。
⇒ 只按 Emphasis 建键，这两条会复用 → PG 拿到 `1`（而 PG 正确值是 `TRUE`）。

### 解析期读 adapter 的**全部**位置（`ExpressionResolver.cs`）
| 行 | 读取 | 方言相关 | 引用开关能影响吗 |
|---|---|---|---|
| 358 / 432 / 476 | `AppendEmphasis`（列名 / 别名） | 是 | **能**（开关 false 且非关键词 → 裸） |
| 129 | `Context.Database.MethodResolver` | 是（且 **SqlServer 按版本**注入） | 否 |
| 548 | `HandleJsonColumn` | 是（每方言一套函数族） | 否 |
| 670 / 675 | `HandleBooleanValue → FormatBooleanValue` | 是（PG/KES = TRUE/FALSE） | 否 |
| 680 | `HandleDateValue`（**基类 abstract，6 个方言各自覆写**） | 是（Oracle `TO_DATE` / PG `TO_TIMESTAMP` / MySql `STR_TO_DATE` / SQLite 裸串） | 否 |

⇒ **"有没有用到 Emphasis"不是判据；判据是"解析结果是不是 Emphasis 的函数"——它不是。**
只要 adapter 的任一解析期行为不同，结果就不同，而身份里只放 Emphasis 覆盖不到。

### 顺带确认的两点
- **关键词兜底确实存在**（引用关也有 Emphasis）：单方言实测 `NoQuoteIdentifiers()` + 列名 `USER`
  → SS `a0.[USER]`、MY `` a0.`USER` ``、ORA `a0."USER"`、PG `a0."USER"`（`USER` 在默认 `keyWorks` 里）。
  非关键词列则一律裸名 → 这部分确实与方言无关。
- **SqlServer V1 vs Over2017 的 `Trim` 分支是冗余的**：`SqlServerMethodResolver.Trim` 的 else 走
  `BaseSqlMethodResolver.Trim`（`BaseSqlMethodResolver.cs:445`），输出同样是 `TRIM(...)` ⇒ 两档输出**逐字节相同**。
  （不是缓存问题，是这条版本分支没有实际差异。）

### ⚠️ 未解释的异常（待查，可能是真缺陷）
多方言同进程（ab8 的 P1）里：先 Oracle 后 PG，PG 的 bool 输出是 `1`（Oracle 的值）而不是 `TRUE`，
且连同 `"ID" AS "Id"` 一起是 Oracle 的整段输出 ⇒ 说明**投影段/该表达式的缓存身份没起作用**。
但同一表达式在单方言进程里两者各自正确 ⇒ 是**跨方言复用**，不是解析错误。
按 `Combine` 的公式 Oracle（有 `IDbResolveIdentity`）与 PG（无 → None=0）本应不同键，故怀疑：
① `IDbResolveIdentity` 在投影段没被探到；② 投影段走的 `ResolveContext.Database` 不是当次 adapter。
—— 这条要单独定位，是"身份是否真的生效"的核心疑点。

### 结论（设计取向）
不要继续枚举属性（已经出现 4 个：Emphasis、引用开关、`keyWorks`、`FormatBooleanValue`/`HandleDateValue`）。
**身份应当默认取"adapter 行为身份"**：穿透 `ScopedDatabaseAdapter` 取 inner 实例身份 + 当次引用开关；
provider 再用 `IDbResolveIdentity` 声明可共享的行为签名（方言+能力位+版本）以恢复跨实例复用。
这样"漏掉某个属性"在结构上不可能发生，而不是靠人肉维护清单。

## 连接超时键名下沉到方言（17:35）

用户指出：`DbVersionProbe.ApplyConnectTimeout` 里那个候选键数组是**方言词汇写在核心** ——
和之前 `DbFeatures` 同一个问题，键名该由方言给。

### 先实测：单键方案够不够（探针，7 个驱动的 `CreateConnectionStringBuilder`）

判定标准三条：赋值不抛异常 / **读回值 == 写入值**（防"静默忽略未知键"的驱动）/ 连接串确实变了。

| 方言 | `Connection Timeout` | `Connect Timeout` | `Timeout` | `ConnectionTimeout` |
|---|---|---|---|---|
| SqlServer | ✅ | ✅（别名） | ✅（别名） | ❌ 不支持的关键字 |
| MySql | ✅ | ✅ | ❌ Option 'Timeout' not supported | ✅ |
| PostgreSQL | ❌ | ❌ | ✅ | ❌ |
| KingbaseES | ❌ | ❌ | ✅ | ❌ |
| Oracle | ✅ | ❌ ORA-50008 | ❌ ORA-50008 | ❌ ORA-50008 |
| Dameng | ❌ does not exist | ✅ | ✅ | ✅ |
| Sqlite | ✅ | ✅ | ✅ | ✅ |

⇒ **每个方言一个规范键即可**：SqlServer/MySql/Oracle/Sqlite = `Connection Timeout`、
Npgsql/Kdbndp = `Timeout`、Dameng = `Connect Timeout`。

⚠️ 注意 `Command Timeout` 在 SqlServer/MySql/PG/KES **四个驱动里都被接受且读回相等** ——
它映射的是**另一个属性**（命令超时），所以"读回校验"并不能区分这两个键。
⇒ 这也是必须让**方言给键**、而不是核心枚举候选的另一个理由：候选法可能挑中语义不同的键。

### 改动

- `DbVersionProbe.Start(...)` 新增必填参数 `string? connectTimeoutKey`，删掉静态 `timeoutKeys` 数组；
  `ApplyConnectTimeout` 改为单键 + **写入后读回校验**（不一致 / 驱动不认这个键 → 放弃改写、沿用原串）。
  核心现在零方言词汇。
- `OracleCapabilities.ConnectTimeoutKey = "Connection Timeout"`（`internal const`，含"不能写成
  `Connect Timeout`/`Timeout`"的注释）；`OracleCapabilities.Start` 传给探测。

### 分支设计（`JsonNativeType` = 原生 JSON 能力，21c+）

| 位置 | 21c+（`JsonNativeType` on） | ≤19c（off） |
|---|---|---|
| `OracleTableHandler.Writer.ConvertToDbType` | 列类型 `JSON` | 列类型 **`CLOB`** |

  ② `JSON_MERGEPATCH` 是**整文档合并**语义，与"设置某个路径"不等价（对象会合并、数组下标无法设置），
  用它会在 ≤19c 上静默产生错误数据；③ 用 `FORMAT JSON` 还能顺带吃到 19.11+ 的回移版
  （那版有 JSON_TRANSFORM 但**没有** `JSON()` 构造器）。
- **未动** `OracleMethodResolver.JsonSet`（`SqlFn.JsonSet` 的口子）：它的值是**用户自己写的 SQL 表达式**

- `MapFeatures(null)` 仍返回 `None` ⇒ 版本未知时退化到**全版本可用**的写法（CLOB + FORMAT JSON）。

回归：Oracle 全量 **18 失败 / 176 通过**，与基线一致；`Select_Result_Test` 单独跑通过（已知 flaky），其余 17 项既有失败 ⇒ **零回归**。核心与 Oracle provider 编译 0 错误。

## MySQL / SqlServer 版本能力梳理（调研，未改代码）

### MySQL（改动面极小）
- 版本只影响 **1 处**：`CustomMySqlAdapter.HandleSelectGroupBySegment:23` 的 `tableOptions.Version > new Version(8,0)`（8.0+ 用 `ROLLUP()/CUBE/GROUPING SETS`，否则 `WITH ROLLUP` 或抛 NotSupported）。
- 缺陷 ①：`MySqlTableOptions.Version` 与基类 `TableOptions.SpecificVersion`（TableGenerateOption.cs:9）语义重复 → 应删 `Version`。
- 缺陷 ②：`>` 严格大于导致 `new Version(8,0)` 与 `new Version(8,0,0)` 都判 false（Build=0 相等）→ 退化成 `WITH ROLLUP`。应 `>= 8.0`。
- 能力位只需 `GroupByRollup`（8.0.0+）。JSON 相关（`JSON` 列类型 5.7.8+、`->>`、`CAST(? AS JSON)`）5.7/8.0 都可用 → **不值得加能力位**（除要支持 5.6）。
- 探测：`DbBaseType.MySql.Name`；`MySqlProvider` 第 40 行才赋值 `DbProviderFactory`，而 handler/adapter 在 34~37 行创建 → 接入须先取 factory（同 Oracle）。

### SqlServer（公开 API 破坏面大）
- 三档枚举 `SqlServerVersion{V1,Over2012,Over2017}` 扩散：`CustomSqlServerAdapter.Paging`（`== Over2012`）、`SqlServerMethodResolver.Trim`（`== Over2017`）、`.Value`（`< Over2017` 抛 STRING_AGG 不支持）；另 IoCExtension 3 重载 + `DatabaseUtils.Avalonia/MainViewModel.cs:36` + **12 个测试文件** + `doc/项目大纲.md:547,550`。
- 缺陷 ①：`Paging` 只判 `== Over2012` → **Over2017 跌回老式 ROW_NUMBER 分页**（`test/LightORMTest.SqlServer/ResultTest/ExecutionTest.cs:10` 正是 Over2017）。能力位化后 Over2017 改走 OFFSET/FETCH → **已生成 SQL 变化，断言分页文本的测试需同步**。
- 缺陷 ②：JSON 完全无版本门控，但 `JSON_VALUE/JSON_QUERY/JSON_MODIFY` 需 **2016(13.0)+** → V1/Over2012 跑 JSON 用例运行期报错。应加 `JsonFunction` 位。
- 能力位：`OffsetFetch`=11.0+、`JsonFunction`=13.0+、`TrimFunction`=14.0+、`StringAgg`=14.0+（**已查证：`WITHIN GROUP` 自 2017 起支持，不是 2022**，现有代码无缺陷）。
- 兼容：`SqlServerVersion` 与 `Create(version,…)` 标 `[Obsolete]` 映射为 `ForVersion`（V1→null 基线 / Over2012→11.0 / Over2017→14.0），主推 `SpecificVersion` + 无版本参新重载。
- 探测：`Microsoft.Data.SqlClient.SqlConnectionStringBuilder.ConnectTimeout`（int）；net462 走 `System.Data.SqlClient`（provider 已有 `#if NET462_OR_GREATER` 模式）。ServerVersion "16.00.1000" → 三段可解析。
- ⚠️ 同进程风险：`LightORMTest.SqlServer` 各测试类共用同一进程且 V1/Over2017 并存，而 `ExpressionResolver` 静态缓存 key 无版本维度 → 同一表达式（如 `Trim`）可能串味命中。该线已按用户要求回滚，**SQL Server 是唯一会真踩的方言**，待重提。

### 连接串超时属性（已核对包内 XML 文档）
- `MySqlConnector.MySqlConnectionStringBuilder.ConnectionTimeout`（**uint**，赋 int 要 cast；同类型还有 `DefaultCommandTimeout`，印证"Command Timeout 也被接受"的坑）
- `Microsoft.Data.SqlClient.SqlConnectionStringBuilder.ConnectTimeout`（int）
- NuGet 全局包目录是 **`F:\nuget\packages`**（不是 E 盘）。

## 落地：SQL Server + MySQL + Oracle 的版本能力重构

### 用户定的口径（重要，后续方言照此办理）
1. **只在"同一功能有多套实现"处才按版本判断**；只有一种实现的**不判版本**，交给数据库报错（"自己抛 NotSupported 和数据库报错差别不大"）。
2. 版本判断**直接比版本分量**（`Major`/`Minor`），不构造 `new Version(...)` 实例比较。
3. 版本探测是**可选功能**：`SpecificVersion` 已指定 / `DetectVersion = false` / 连接串为空 → 都不探测。探测失败与这些出口同结果。
4. 唯一索引/约束等 DDL 能力若存在版本差异（如 MySQL 函数索引仅 8.0.13+）也要按此口径考虑。

### 基类
`TableOptions` 新增 `bool DetectVersion { get; set; } = true`（`DbStruct/TableGenerateOption.cs`），与 `SpecificVersion` 并列。

### SQL Server
- **删除 `SqlServerVersion` 枚举**（V1/Over2012/Over2017），`SqlServerProvider.Create` 不再收版本；`IoCExtension` 的 3 个 `UseSqlServer` 重载简化成 2 个（去掉带 `key` 的那个——它会与 `(string master, params string[])` 产生重载歧义），连带改 `DatabaseUtils/WpfApp.razor.cs`、`DatabaseUtils.Avalonia/MainViewModel.cs` 与 11 个测试文件。
- 新增 `SqlServerCapabilities`（`SqlServerFeatures`）：**只保留 2 个位**——`OffsetFetch`（2012+，`OFFSET/FETCH` vs `ROW_NUMBER` 包裹）、`TrimFunction`（2017+，`TRIM()` vs `LTRIM(RTRIM())`）。原 `JsonFunction`/`StringAgg` 按口径删除（JSON 函数仅 2016+、`STRING_AGG` 仅 2017+，都只有一种写法）。
- 基线：**乐观（未知 → Full）**。理由：这两个位都是"新写法在旧库报错、旧写法在新库仍可跑"。
- `SqlServerMethodResolver` 构造改收 capabilities（另留无参构造 = Baseline）；`CustomSqlServerAdapter` 同。
- **修了一个被新代码暴露的既有缺陷**：`OFFSET/FETCH` 要求前面必须有 `ORDER BY`，否则 `Incorrect syntax near 'OFFSET'` / `Invalid usage of the option NEXT`。老代码 `Paging` 只判 `== Over2012`，而测试用的是 `V1`/`Over2017` → 全走 ROW_NUMBER 分支，**新式分页从未被执行过**；接上探测后（探测到 16.0）才第一次真正生成。修法：`builder.OrderBy.Count == 0` 时按主键补 `ORDER BY`（`SelectBuilder` 正是 `OrderBy.Count > 0` 才写 ORDER BY，信号精确）。
- 测试（262 用例）：改动后全量 18 失败 → 修分页后 `Select_Paging_Test` 两个副本**单独跑均通过**（640ms/627ms）。剩余失败原因分类：10 个是 `InitDatas` 里 `DROP TABLE` 锁超时（级联/环境）、其余是既有表达式 bug（`The binary operator Equal is not defined for types 'String' and 'Nullable[DateTime]'`、`IndexOutOfRangeException`、`Static property requires null instance`）。**没有任何一个错误是 SQL 语法/函数不支持**。
  - 判既有失败的好证据：`TestRowNumberWindowFunc` / `TestSelectOneTable` / `TestArrayAccess_List` / `Select_Navigate_Where_Single` 在 **SqlServer、Oracle、MySQL 三个方言同时失败**，错误一致，且都与版本能力位无关。

### MySQL
- **删除 `MySqlTableOptions.Version`**（与基类 `SpecificVersion` 重复），新增 `MySqlCapabilities`（`MySqlFeatures`）：只 1 个位 `GroupByRollup`（8.0+，`ROLLUP()/CUBE/GROUPING SETS` vs `WITH ROLLUP`）。
- 基线：**保守（未知 → None）**。理由：旧写法 `WITH ROLLUP` 在 5.7/8.0 都能跑，而 8.0 的 `ROLLUP()` 语法在 5.7 直接报错。顺带修了 `Version > new Version(8,0)` 的边界 bug（`8.0`、`8.0.0` 都判 false），现在用 `Major >= 8`。
- `CustomMySqlAdapter` 的 `HandleSelectGroupBySegment` 简化：8.0+ 走 base；8.0 以下只有 `IsRollup` 时生成 `GROUP BY (...) WITH ROLLUP`，**CUBE / GROUPING SETS 不再抛 `NotSupportedException`**，走 base 生成后交给 MySQL 报错（按口径）。
- MySQL 超时委托：`MySqlConnectionStringBuilder.ConnectionTimeout`（**uint**，要 cast；同类型另有 `DefaultCommandTimeout` → 再次印证"按键名试探分不清语义"）。
- 测试（158 用例）：失败 9 / 通过 149。原因：4 个 CTE（5.7 无 CTE）、1 个 `Group_Cube_Test`（5.7 无 CUBE，旧代码在 5.7 下同样失败，只是异常类型从 `NotSupportedException` 变成 MySQL 语法错）、4 个既有表达式 bug（与另两个方言同名用例一致）⇒ 与本次改造无关。

### Oracle（按同一口径回审）
- 两个位都符合"有多套实现"：`IdentityColumn`（IDENTITY vs 序列+触发器）、`JsonNativeType`（`JSON` 列 + `JSON()` vs `CLOB` + `FORMAT JSON`）→ 都保留。
- 接入 `DetectVersion`：`OracleCapabilities.Start(factory, cs, specificVersion, detectVersion)`；`OracleProvider` 传 `generate.DetectVersion`。
- `MapFeatures(Version? version, string? raw)` 的 **`raw` 参数无用已删**。
- 顺带修边界：`Major >= 12 && Minor >= 1` 会漏掉 minor=0 的 12.1+ 版本 → 改为 `Major >= 13 || (Major == 12 && Minor >= 1)`。
- 回归：194 用例 **18 失败 / 176 通过，与基线一致**；失败类型为 ORA-00054 资源正忙、ORA-12704 字符集不匹配、ORA-00904 `"B0"."UserId"`（CTE 别名，与 SqlServer 的 `'UserId'` 同源）等，均与能力位无关。

### 待议
- MySQL 的**函数索引（8.0.13+）**：当前 `DbIndex.Columns` 只是列名字符串列表，框架没有函数索引生成点（`LightTableIndexAttribute(params string[] indexs)` 由用户手写），所以暂无能力位可用之处。若将来要支持"5.7 需要索引前缀长度"这类降级，再作为 `MySqlFeatures` 的新位加入。
- 其余方言（PostgreSQL / KingbaseES / Dameng / Sqlite）尚未接入探测。

## 实测：`DetectVersion = true` 的真实开销（MySQL 5.7.44 本机，探针测完即删）

| 观测点 | 耗时 |
|---|---|
| 探测开启 #1 构造 | 60.10 ms（**驱动首次初始化/JIT 占大头，与探测无关**） |
| 探测开启 #1 **首次读 ServerVersion** | **32.97 ms** ← 等一次建连，`5.7.44 [Probed]` |
| 探测开启 #1 次读 Features | 0.230 ms（这 0.23ms 是首次 JIT） |
| 探测开启 #1 读 Features × 100000 | 5.95 ms ⇒ **≈60 ns/次** |
| 探测开启 #2 构造（**同连接串**） | 0.16 ms |
| 探测开启 #2 首次读版本 | 0.000 ms |
| 探测关闭 构造 / 首次读版本 | 0.62 ms / 0.000 ms（`Assumed`） |
| 换连接串（不同 Database）构造 / 首读 | 1.40 ms / 5.96 ms |
| 裸建连（池化）建连+读版本（对照） | 5.66 ms |

**结论**：稳态读取零开销（~60ns）；那 30~40ms 只发生在**每个连接串在进程内第一次读取版本时**（= 等待一次建连）。
同连接串的第二个 provider 构造 0.16ms、首读 0ms ⇒ 用户看到的「180ms → 220ms」是**每进程（每连接串）一次**，不是每用例。
可消除该开销的既有手段：`SpecificVersion`（显式指定，零建连零等待）或 `DetectVersion = false`（走基线）。
若想连这次建连也省掉，只有"用业务已打开的连接回填 ServerVersion"一路，但**首次生成的 SQL 会落在基线上**——SqlServer 的乐观基线在 2012 以下是错的（会生成 OFFSET/FETCH），故未采用。
