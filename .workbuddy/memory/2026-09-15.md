## Oracle JSON 能力的版本门槛（查证结论）

| 能力 | 最低版本 | 说明 |
|---|---|---|
| JSON 文本存 VARCHAR2/CLOB/BLOB + `JSON_VALUE`/`JSON_QUERY`/`JSON_EXISTS` 查询 | 12.1.0.2 | "文本当 JSON 用"，路径只读 |
| `JSON_MERGEPATCH` | 19c | 整文档合并式更新；数组只能整体替换，无法把单键 SET 成 null |
| 原生 `JSON` 数据类型（OSON 二进制） | 21c | 20c 仅云上预览，21c 正式 GA |
| `JSON_TRANSFORM`（路径级 SET/REMOVE/RENAME/APPEND） | **21c** | 框架路径更新的唯一依赖 |
| `JSON()` 构造器 / `JSON_SCALAR` / `JSON_SERIALIZE` / JSON 多值函数索引 | 21c | |

**对框架的结论**：路径级 json 更新（`SET '$.a' = ...`）**必须 21c+**，≤19c 只能整列替换。
`OracleTableHandler.Writer.ConvertToDbType` 默认把 json 列建为原生 `JSON`（21c+），≤19c 建表即失败
—— 这是"Oracle 库不支持 json 列"的根因。≤19c 的绕过手段是 `OracleTableOptions.SpecificJsonColumnDbType`
显式给 `CLOB`/`VARCHAR2(n)`，此时只能整列读写、无路径更新能力。

## 补齐 Oracle json 三处缺口

文件：`src/Providers/LightORM.Providers.Oracle/CustomOracleAdapter.cs`

1. **整列 Update 分支缺失** → 补 `!context.HasIndexInfo()` 分支，生成 `"JSON_DATA" = :Json`。
   原实现无条件 `JSON_TRANSFORM(col, SET '$' = :p)`，两个致命问题：JSON_TRANSFORM 对 NULL 输入
   返回 NULL（列被置空后写不回，与已修的 MySQL `JSON_SET(NULL,...)` 同类）；`SET '$'` 的文本参数
   按 JSON 字符串写入（双重编码）。
2. **路径更新值参数未按 JSON 解析** → 改为 `SET '$.a' = JSON(:p)`。框架下发的参数是
   `JsonParameterHelper.Serialize` 后的 JSON 文本，直接赋值会被当 JSON 字符串。与 SQLite 的
   `JSON(@p)`、PG 的 `@p::JSONB` 同一约定。
3. **缺 `IDatabaseParameterBinder` 覆写** → 补 `BindParameter`：json 列一律序列化并绑
   `OracleDbType.Clob`（VARCHAR2 绑定有 4000 字节上限，超长文档 ORA-01461）。

`OracleMethodResolver.JsonSet` **保持不动**：其值是用户原始值、不走 binder，Oracle 侧
`SET '$.a' = 'test'` 恰好把字符串写成 JSON 字符串，与执行用例期望一致。

## 遗留观察（未改）

Oracle 非 Update 分支（读取路径）仍用 `JSON_VALUE`：只返回标量，取对象/数组会得到 NULL，且默认
`RETURNING VARCHAR2(4000)` 对长文本截断。PG 侧是按末级成员类型分流 `->` / `->>` + cast 的，Oracle
可考虑对齐为「标量 `JSON_VALUE` / 复合 `JSON_QUERY`」。

### 恢复手法（可复用）：按内容识别并回填 git 对象

`$I` 的名字不可靠，但 git 松散对象是**自校验**的 —— 只要按内容算出 SHA-1，就能反推它该落在哪个路径。
脚本 `C:\Users\Marvel\AppData\Local\Temp\recover_git_objects.ps1`（PowerShell，因沙箱禁止 Python 读 `$RECYCLE.BIN`）：

1. 枚举 `E:\$RECYCLE.BIN\<SID>` 与 `C:\$Recycle.Bin\<SID>` 下所有 `$R*` 文件（`< 32MB`）；
2. 按 zlib 头筛选（`0x78` + `01/5E/9C/DA`），`DeflateStream`（跳过 2 字节头）解压；
3. 解压结果以 `blob `/`tree `/`commit `/`tag ` 开头 ⇒ 是 git 对象；
4. 对该**解压后内容**求 SHA-1 → 十六进制即为对象 ID；
5. 目标路径 `.git\objects\<前2位>\<后38位>` 不存在则复制过去（**只增不改，天然安全**）。

结果：`scanned=29654 zlib=382 gitobj=382 restored=382 exist=0` —— **恢复 382 个对象**
（178 blob / 163 tree / 41 commit），其中包含 `97735c30`（docs 提交，即 HEAD）与 `809f6394`。
