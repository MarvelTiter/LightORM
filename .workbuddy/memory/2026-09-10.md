# 2026-09-10 LightORM 工作日志

## json 列"整列更新 / JsonSet 路径更新"解析问题定位 (用户要求: 先别动代码, 只分析)

### 用户给出的方向
- 问题: 解析 json 列无法处理 **json 全列更新** 或 **json 路径更新**。
- 修复位置: `ExpressionResolver.VisitMember` 解析到 json 列时必须调用 `HandleJsonColumn`。
- 当 `Indexer == null` 或 `Members.Count == 0` 时, 既可能是整列更新, 也可能是 json 路径更新(调用 `SqlFn.JsonSet`)。

### 已核实的代码事实 (PG only)
- `src/LightORM/Utils/ExpressionResolver.cs:520-533` json 分支守卫:
  `if (col.IsJsonColumn && !specificHandleJson) { var index = GetResolvedIndex(); ResolvedMembers.Add(col.PropertyName); if (index.HasValue || Members.Count > 0) { ...HandleJsonColumn...; return null; } }`
  → **index 无值 且 Members 为空时不调用 HandleJsonColumn**, 直接落到 line 547-560 普通列路径, 只 `Sql.AppendEmphasis(col.ColumnName)` → `result.SqlString` = 裸列名 `"DATA"`。
  (git diff 显示该守卫刚由"两段 if"合并为 `index.HasValue || Members.Count > 0`, 新增了"带索引也走 HandleJsonColumn")
- `specificHandleJson` 仅由 `JsonQuery` 置位: ExpressionResolver.cs:307-312 `if (exp.Method.Name == "JsonQuery") specificHandleJson = true;` → **JsonSet 未置位**。
- 整列更新落点: `UpdateBuilder.cs:82-85` 对 json 列 `UpdateSpecific.Add(col.PropertyName, result.SqlString)`(直接存 result.SqlString, 期望它是"完整赋值"); 构建时 `UpdateBuilder.cs:289-291` `sb.Append(fieldSql)` 直接拼 → 得到 `SET "DATA"` (缺 `= @p`)。对比非 json 列 line 88 显式拼 `= @prefix`。
- PG `HandleJsonColumn` 已实现两种 Update 语义 (CustomPostgreSQL.cs:75-134):
  - `context.HasIndexInfo()` 为 true → `col = JSONB_SET(col::JSONB, '{路径}', @Prop::JSONB)` (路径更新)
  - false → `col = @Prop::JSONB` (整列更新, CustomPostgreSQL.cs:129-133)
  `HasIndexInfo()` = `Members.Count > 0 || Members.Any(i => i.IndexValue.HasValue)` (JsonColumnContext.cs:15-18)。
- PG `JsonSet` resolver (PostgreSQLMethodResolver.cs:210-238) 自己会 `Visit(Arguments[0]); " = "; "JSONB_SET("; Visit(Arguments[0]); "::JSONB"; ...` → 即"列实参"期待是**裸列名**, 且它自己发 `col =` 和 JSONB_SET。

### 结论 / 待确认的修复方案
- 空分支的三种形态: (1) 整列更新 `Set(j=>j.Data, obj)` 需要 `col = @Prop::JSONB`; (2) `SqlFn.JsonSet(j.Data, path, v)` 的列实参需要**保持裸列名**(由 PG.JsonSet 自己拼赋值, 否则双重赋值 `"DATA" = @Data::JSONB = JSONB_SET(...)`); (3) Select/Where 裸引用 `j.Data` 应保持裸列名。
- 方案: (a) VisitMember 在 `!index.HasValue && Members.Count == 0` 且 `SqlType == SqlPartial.Update` 时也调用 HandleJsonColumn; (b) 同时把 `JsonSet` 纳入 `specificHandleJson = true`(与 JsonQuery 一致)以免 (a) 误伤 JsonSet 的列实参; (c) 限定 Update 以免 Select/Where 裸引用被包成 `("DATA")`。
- 未动代码, 等用户确认方向。

### json 整列/路径更新修复 (仅 PG; 用户: UpdateColumns 也走 Update 分支, SetNull 走 SetNullMembers; 其他 provider 稍后)
- 根因: ExpressionResolver.VisitMember 中 json 列分支当 `index 无值 && Members 为空` 时直接落普通列路径 → 输出裸列名; UpdateBuilder 整列 json 走 UpdateSpecific.Add(prop, result.SqlString) 要求 result.SqlString 是完整赋值 → 生成 `SET "DATA"` 缺 `= @p`。
- 改动1 `ExpressionResolver.VisitMethodCall`(~306): JsonQuery 与 JsonSet 都置 specificHandleJson=true (用 isSpecificJson 局部变量, resolve 后恢复)。作用: JsonSet 的列实参保持裸列名, 避免被 VisitMember 的新整列分支二次包装成 `col=@p = JSONB_SET(...)`。
- 改动2 `ExpressionResolver.VisitMember`(~536): 空分支条件加 `|| Options.SqlType == SqlPartial.Update` → Update 下整列引用也调用 HandleJsonColumn。仅限 Update(Select/Where/Insert 裸引用 json 列语义不变)。
- 改动3 `CustomPostgreSQL.HandleJsonColumn` 整列分支(~127): 补 `context.Sql.Append(Prefix)` → `"DATA" = @Data::JSONB`(原来漏 @, 生成 `= Data::JSONB`)。
- 编译: core 全 TFM + PG net462/net8.0/net10.0 均 0 错误。
- Sqlite 冒烟(--filter ~Json): 15 通过 / 3 失败。整列 UPDATE 现在生成合法 SQL `SET \`DATA\`=JSON_SET(\`DATA\`,'$',@Data),...`(修复前为非法 `SET \`DATA\`,...`)。剩 3 失败(NestedPath_Update / WholeColumn_Update / TestJsonUpdateAsync)均为 Sqlite json 更新"值被双引号/双重编码"的方言问题(修复前同样失败, 非回归); JsonColumn_JsonSet_Update 现通过。
- 注意: 改动2 是框架级, 影响所有 provider 的 Update 整列 json; 非 PG 方言 HandleJsonColumn 空分支行为(如 Sqlite JSON_SET(col,'$',@v) )待后续按各自能力复核。更新入口依赖 build 阶段 UpdateBuilder:289-297 序列化 + binder 类型化闭环(无需改 UpdateBuilder)。

## UpdateColumns json 列最终修法 (推翻上一节的 UpdateSpecific 兜底方案)
- 用户: "补充测试用例" → 补 `JsonColumn_UpdateColumns_MultiColumns_Update`(Data+Obj 两列)。
- 多列实测畸形 SQL: `SET \`DATA\`=JSON_SET(...,@Data), \`OBJ\`=JSON_SET(...,@Obj), \`OBJ\`=@Obj` —— 根因: `VisitNew` 把多列赋值累积进同一个 `result.SqlString`, 而 `HandleResult` 只按 `Members[0]`(Data) 存进 UpdateSpecific, 其它成员又走普通列路径重复生成。
- **最终方案(已落地)**: 给 UpdateColumns 的 ExpressionInfo 打标记, 让它按"纯列选择"处理。
  1. `src/LightORM/Models/SpecificValue.cs`: 新增 `internal class UpdateColumnsFlags`(私有构造 + `Instance`, 仿 `GroupingSetsFlags`)。
  2. `UpdateProvider.UpdateColumns<TUpdate>`: `new ExpressionInfo(SqlResolveOptions.Update, columns, additionalParameter: UpdateColumnsFlags.Instance)`。
  3. `UpdateBuilder.HandleResult`: Update 分支新增 `else if (expInfo.AdditionalParameter is UpdateColumnsFlags) { Members.AddRange(result.Members); }` —— 忽略解析出的整列赋值 SqlString, 只登记成员。
  4. 回退上一节在 `ToSqlString` 的 `UpdateSpecific` json 列为 TargetObject 兜底的改动(已无必要, 恢复原样)。
- 效果: json 列在 UpdateColumns 下走普通列路径 → `col = @p`, 值由主流程 `c.GetValue(TargetObject)` + 序列化 + `DbParameterValue(col, json)` 交给方言 binder 类型化(PG → jsonb)。不需要 `::JSONB` 转换, 也不走 `JSON_SET`。
- **为什么不用枚举方案**: 曾考虑让 UpdateColumns 用未使用的 `SqlPartial.UpdatePartial` 区分(枚举值确认全库无引用), 但 `ExpressionExtensions.Resolve` 的缓存键是 `CacheKey(SqlAction, Hash, NestedLevel)` **不含 SqlPartial**, `j => j.Data` 在 Set 与 UpdateColumns 下 hash 相同 → 会串缓存, 故放弃。标记走 AdditionalParameter, 不触碰解析器与缓存。
- 验证:
  - Sqlite `--filter "~Update|~Json"`: 36 用例 / 33 通过 / 3 失败。`JsonColumn_UpdateColumns_Update`、`JsonColumn_UpdateColumns_MultiColumns_Update`、`SetNull`、`Set(col,null)`、`Update_Columns_Test`、`UpdateTest`、`Update_Batch` 全部通过。
  - 剩余 3 失败=`JsonColumn_NestedPath_Update` / `JsonColumn_WholeColumn_Update` / `TestJsonUpdateAsync`, 全是 Sqlite 走 `JSON_SET` 的**双重编码**(json 文本被再包一层字符串), 与本次改动无关。线索: Sqlite `HandleJsonColumn` 整列分支用 `JSON_SET(col,'$',@p)` 是错的, 应该直接 `col = @p`(UpdateColumns 用普通列路径就是 `= @p`, 读回正常)。
  - PG SQL 生成(SqlGenerate 不需要真库): `UPDATE JSON_TEST SET JSON_DATA = @Json WHERE (ID = @Id)`, 参数 `Json - {"Name":"ColsName",...}`; 多列 → `JSON_DATA = @Json, JSON_DATA_ELEMENT = @JsonObject`, 无重复列。
  - 编译: core 全 TFM 0 错误; PG 测试项目 0 错误。
