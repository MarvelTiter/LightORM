## AOT 裁剪：ODP.NET InitialLONGFetchSize NRE 根因与修复（已验证）

- 现象：调试正常，AOT 发布后 `CustomOracleAdapter.DbCommandInit` 中 `oracleCommand.InitialLONGFetchSize = -1` 抛 NRE。
- 根因（反编译 Oracle.ManagedDataAccess.Core 23.26.200 确认）：`OracleCommand` 的 `FetchSize`/`RowsToFetchPerRoundTrip`/`InitialLOBFetchSize`/`InitialLONGFetchSize` 四个 setter 开头都有 `MethodInfo setMethod = GetType().GetProperty("...").SetMethod;`。实例 `GetType()` 的反射目标裁剪器无法静态解析 → 属性元数据被裁掉 → `GetProperty` 返回 null → `.SetMethod` NRE。`BindByName` setter 无反射，不受影响（与现象吻合）。
- 修复（已用最小 AOT repro 验证，repro 在 `.workbuddy/tmp/AotOracleTest/`）：消费端 csproj 加 `<TrimmerRootAssembly Include="Oracle.ManagedDataAccess" />`，发布后两步全过（ALL_PASSED）。
- 残余风险：IL3053（Oracle 程序集未做 AOT 注解）、多处 IL3000（single-file 下 `Assembly.Location` 为空）。若后续 Open/ExecuteReader 再出现 NRE，同一机制，优先继续用 Trimmer 根解决。
- 治本备选：给 LightORM.Providers.Oracle 的 NuGet 包加 buildTransitive targets，自动注入 TrimmerRootAssembly（待用户确认是否要做）。

## ExpressionBuilder 裁剪安全诊断（用户问"如何保证"，核心洞已定位）

- **真洞（会 NRE）**：`ExpressionBuilder.ReflectMethod.cs:39-46` 用 `typeof(ExpressionBuilder).GetMethod(nameof(...))` 反射取 7 个同类型 helper（RecordFieldToUInt16/32/64、RecordFieldToBytes、CustomStringToBoolean、RecordFieldStringDeserializer、RecordFieldBytesDeserializer）。`nameof` 是编译期字符串、不产生直接调用 → 裁剪器视为无引用 → 这些方法被裁 → GetMethod 返回 null → 遇 uint/ulong/byte[]/bool/JSON 列首次读取即 NRE。且**全库仅 DbParameterReader.cs:121 有一处 [DynamicDependency]**，这 7 个方法无 DynamicDependency 无直接调用方。
- **全库裁剪/抑制现状**：几乎全靠 `[UnconditionalSuppressMessage(IL2xxx/IL3050)]` 压警告，它只隐藏不保留成员（DBParameterReader 121-122 例外，有真 DynamicDependency）。ResolveHelper/ObjectExtensions 的 Type 形参缺 DAM。
- **保裁剪的三类工具映射**（讲给用户的答案）：① 同类型 helper → 用 `[DynamicDependency]` 锚定或改直接引用（nameof 不 root、Suppress 不保留）；② 固定 BCL 方法（IDataRecord/Convert/Parse）→ BCL 自带标注，若走 Convert.GetMethod 需给泛型参 DAM 让编译器静态追踪；③ 运行时 T/reader 成员（T 属性/嵌套/Flat/列转换目标）→ 唯一不可静态化的"开放集"，只能靠入口泛型 DAM 流动 + 承认"保不住就查询时崩"。
- ExpressionBuilder.cs 运行时分支断点行号见 v3 报告：GetFieldType(301)/AllowDBNull(302)/typeMapMethod(380)/转换对(417-456)/IsEnum(495)。

## 机制再修正：Expression.Compile 在 AOT 下是解释模式，真风险是运行时分支（v3 报告）

- 用户纠正：`Expression.Compile()` 在 NativeAOT 下**并非不可行，而是退化为解释模式执行**（能跑，性能损失 + 每新 schema 现场造树开销），不是 IL3050 那种硬阻断。
- 真风险：反序列化**入口唯一**（BuildDeserializer<T>），但内部调用路径要等 `DbDataReader` 实例在运行时才能确定——每列走哪条 `GetXxx`/转换分支由 `reader.GetFieldType`(ExpressionBuilder.cs:301)/`GetSchemaTable AllowDBNull`(302)/`typeMapMethod.TryGetValue`(380)/`(SourceType,TargetType)`转换对(417-456)/`IsEnum`(495) 现场决定。裁剪器无法静态分析这条运行时链 → 只能靠边界 DAM(19/75) + IL 抑制(141) 兜，静默裁错则查询时才崩。
- 结论：`IsAotCompatible=true` 覆盖「编译产物标注兼容」，覆盖不了「运行时才展开的调用路径」。doc/aot-risk-analysis.md 已重写为 v3（机制修正）。作者仍不新增静态反序列化方案。

## 用户澄清：CreateDeserializeMethod 是废弃内容（修正上面 P0 判断）

- 作者明确：生成器的 `DataReaderDeserializer`/`CreateDeserializeMethod`（CreateDeserializeMethod.cs throw NotImplementedException）是**废弃内容**，不是未来方向，也不代表反序列化缺口。
- 修正：反序列化现状=运行时 ~18 个映射调用点唯一走 `ExpressionBuilder.BuildDeserializer<T>` → `Compile()`，**无任何静态/生成路径**，AOT 下动态编译——这是**已声明搁置的技术债**，不是"待填桩的功能"。doc/aot-risk-analysis.md 已修订为如实标注 + 剔除指向废弃方向的整改项。
- 附带确认：`DeserializerCache.cs` 空实现零消费；`TableContextGenerator.cs:11-37` 用 `ModuleInitializer`+`LightOrmTableContextBase.AddTable` 做静态注册的方案被注释停用；`IsAOTRuntime` 判断不在映射边界（只拦 object 匿名参数和嵌套匿名），具名实体映射无 AOT 护栏。
- 合理兜底（不改反序列化）：在 BuildDeserializer<T> 边界加 IsAOTRuntime 显式抛错前置失败，并让 LightOrmAotAnalyzer 对结果映射升级为 Error。
