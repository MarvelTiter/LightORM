## 批量写入的 json 列支持 (用户: 批量场景下 json 列都是整列更新, 通过改 ToDictionaryParameters 支持; 补测试用例)

- 用户假设核实: **成立**。批量 Insert/Update/Upsert 的值全部来自实体属性或 `Set(col, 单值)`, 不存在 json 路径/索引表达式 → 一定整列赋值。
- 原状:
  - `UpdateBuilder.CreateUpdateBatchSql` 显式 `if (col.IsJsonColumn) return false;`(带 `// TODO 批量更新对JSON列处理`) → 批量更新**完全跳过** json 列。若实体只有主键 + json 列, 过滤后 `columns` 仅剩主键, SET 循环 `if (col.IsPrimaryKey) continue;` 全跳过 → 生成 `UPDATE T SET WHERE ...` 畸形 SQL(Sqlite 报 `SQL logic error`)。
  - `InsertBuilder` 不排除 json 列, 但 `BatchSqlInfoExtensions.ToDictionaryParameters` 直接 `new(col.Column, col.Value)` 传原始对象 → Sqlite 驱动按 ToString() 入参, 读回报 `JsonException: 'L' is an invalid start of a value`(写进去的是 `LightORMTest.Models.JsonData` 之类的类型名)。
  - `Dictionary<string,object>` → `Dictionary<string,DbParameterValue>` 的返回类型改动此前已完成(git diff 可见), 但仅改类型不足以支持 json, 必然还要序列化。
- 改动(4 处):
  1. `src/LightORM/Builder/UpdateBuilder.cs` `CreateUpdateBatchSql`: 删除 json 列排除, 让 json 与普通列同走 `col = CASE WHEN 主键 = @p THEN @val ... END`。
  2. `src/LightORM/Extension/BatchSqlInfoExtensions.cs` `ToDictionaryParameters`: json 列先 `GetJsonHandler().Serialize(value)` 成 JSON 文本再入字典; 且 json 列即使 `IsStaticValue` 也要下发(静态值通常内联字面量, 但 json 无法渲染), 该判断用 `if (col.IsStaticValue && !col.IsJsonColumn) continue;`。
  3. `src/LightORM/Extension/CustomDatabaseExtensions.cs` `AppendSimpleColumnValueExpression`: `IsStaticValue` 分支加 `&& !col.IsJsonColumn` → json 列统一走参数(否则 `FormatStaticValue` 对 JsonData 抛 `NotSupportedException`)。
  4. `InsertProvider`/`UpdateProvider`.`ToSqlWithParameters` 批量行数据打印按序列化后的值显示(调试输出保真)。
- 新增测试:
  - `test/LightORMTest/ResultTest/ExecutionTest.JsonColumnCases.cs`: `JsonColumn_BatchInsert_ReadBack`(200/201)、`JsonColumn_BatchUpdate_WholeColumns`(210/211)、`JsonColumn_BatchInsertOrUpdate_WholeColumns`(220/221)。
  - `test/LightORMTest/SqlGenerate/InsertSql_Json.cs` `InsertJsonModel_Batch`; `SqlGenerate/UpdateSql_Json.cs` `UpdateJsonModel_Batch`(仅打印, PG 项目不连库即可跑)。

    - 批量 Insert → `INSERT INTO JSON_TEST (ID,JSON_DATA,...) VALUES (@Id_0,@Json_0,...),(@Id_1,...)`
    - 批量 Update → `UPDATE JSON_TEST SET JSON_DATA = CASE WHEN ID = @Id_0 THEN @Json_0 WHEN ID = @Id_1 THEN @Json_1 END WHERE (ID IN (@Id_0,@Id_1))`, 无重复列

  `Db.Update([e1,e2]).Set(j => j.Json.NestJson.Name, "PathProbe")`

## SQLite json 路径更新的"双重编码"修复 (用户: json 值是字符串时参数从 string → "string", PG 读取有 ::TEXT 转换没问题, SQLite 没有, 读回带引号)

- 复现(默认 Sqlite 后端 JSONBackend=Text):
  ```
  UPDATE `JSON_EXEC_TEST` SET `DATA` = JSON_SET(`DATA`,'$.NestJson.Name',@Data) WHERE (`ID` = 101)
  参数: Data - "NewNest"      ← 框架序列化后带引号
  读回: ""NewNest""           ← 期望 "NewNest"
  ```
  用例: `JsonColumn_NestedPath_Update`(`Set(j => j.Data!.NestJson!.Name, "NewNest")`), 此前是 Sqlite 唯一失败用例。
- **根因**(用 Python sqlite3 3.53 实测确认):
  - SQLite `json_set(X,P,V)` 对 **TEXT 类型的 V 按"字符串字面量"处理, 不会把它当 JSON 解析**:
    `json_set('{}','$.a','"abc"')` → `{"a":"\"abc\""}`(双重编码); `json_set('{}','$.a','abc')` → `{"a":"abc"}`。
    要用 JSON 值必须显式 `JSON(V)` 包装: `json_set('{}','$.a', JSON('"abc"'))` → `{"a":"abc"}` ✓(对象/数字/null 同理)。
  - 而框架对 json 列参数**统一序列化为 JSON 文本**(`ActionType.ParameterValue` 注释即 `'string' => '"string"'`), 对 PG 的 `@p::JSONB` 是必须的, 对 SQLite 就成了双重编码。
  - `JSON_EXTRACT` 读取会自动脱壳(返回 `abc`), 所以症状表现为"读回多一层引号"。
- 修复(仅 1 处, Sqlite):
  `src/Providers/LightORM.Providers.Sqlite/CustomSqliteAdapter.cs` `HandleJsonColumn` 更新分支:
  `JSON_SET(col,'$.path',@p)` → `JSON_SET(col,'$.path',JSON(@p))`。
  生成结果: `` `DATA` = JSON_SET(`DATA`,'$.NestJson.Name',JSON(@Data)) ``。
- **不受影响的路径**(已核对): 整列更新走 else 分支 `col = @p`(存 JSON 文本, 读取反序列化, 对称); `SqlFn.JsonSet` 走 `SqliteMethodResolver.JsonSet`, 值参数是**用户原始值**(未序列化)故不能用 `JSON()` 包装 —— 即 `Set(路径,值)` 与 `SqlFn.JsonSet(路径,值)` 的参数语义不同(PG 侧 JsonSet 需用户给 JSON 文本, 测试里手写 `"\"NewName\""`), 属既有设计, 未动。
- 新增用例: `ExecutionTest.JsonColumnCases.cs` → `JsonColumn_ScalarAndIndexPath_Set_Update`(Id=102, `Set(j.Data.Value, 4321)` + `Set(j.Arr[1].Name, "ArrItem1")`, 覆盖数字标量与数组索引路径)。注意 `Arr` 是**模型列**不是 `JsonData` 成员。
- 验证: Sqlite `JsonColumn*` **15/15 全绿**; `~Json|~Update` 39/39; core 全 TFM + PG 测试项目 + Sqlite provider 库 全 0 错误; PG 生成 SQL 未变(PG 走 `::JSONB`, 本来就正确)。
- **其他方言同类隐患(未改, 待用户决策)**: 框架统一传"序列化 JSON 文本", 但方言对 TEXT 参数的 JSON 解析规则各异 —— MySql `JSON_SET`、SqlServer `JSON_MODIFY`(对字符串会再加引号)、Oracle `JSON_TRANSFORM` 都需要额外的显式解析(如 MySQL `CAST(@p AS JSON)`、SQLServer `JSON_QUERY(@p)`), 否则同样双重编码。无实库未验证。

## SqlServer 的 json 路径更新 (用户: sqlserver怎么处理)

- 本机有 **LocalDB 2019**(SQL Server 2019 Express 15.0.4382.1), 可 sqlcmd 实测:
  `"/c/Program Files/Microsoft SQL Server/Client SDK/ODBC/170/Tools/Binn/sqlcmd" -S "(localdb)\MSSQLLocalDB" -E -i x.sql -W -s"|" -h-1`
  (坑: 整个 .sql 文件是**一个批**, 一条语句出错就中止 → 必须用 `GO` 分批; `localhost` 连不上, 报"安全包中没有可用的凭证/Cannot generate SSPI context")
- **`JSON_MODIFY` 实测语义**(第三参数 → 结果):
  | 传入 | 结果 | 判定 |
  |---|---|---|
  | `'"abc"'`(序列化文本) | `{"a":"\"abc\""}` | ✗ 双重编码 |
  | `'abc'`(裸文本) | `{"a":"abc"}` | ✓ |
  | `'{"k":1}'` | `{"o":"{\"k\":1}"}` | ✗ 对象变字符串 |
  | `JSON_QUERY('{"k":1}')` | `{"o":{"k":1}}` | ✓ |
  | `'4321'` | `{"n":"4321"}` | ✗ 数字变字符串 |
  | `4321`(int) | `{"n":4321}` | ✓ |
  | `CAST(1 AS bit)` | `{"b":true}` | ✓ |
  | `NULL` | 删除该键 | ⚠️ 无法写 JSON null |
- **SQL Server 的 JSON 函数只认"根为对象/数组"的文本**: `ISJSON('"abc"')=0`、`ISJSON('4321')=0`(`{}`/`[]`=1); `JSON_QUERY('"abc"')` / `JSON_VALUE('"abc"','$')` **抛 Msg 13609**(不是返回 NULL)。`JSON_VALUE('["abc"]','$[0]')` = `abc` 可脱壳, 但数字出来仍是 nvarchar。
- **无 SQL 侧通用解**: `sql_variant` 被 `json_modify` 拒绝(Msg 8116; nvarchar(max)→sql_variant 也不允许 Msg 529); CASE 多分支**类型统一**(nvarchar 优先)→ 数字退化字符串、对象转 float 报 8114。
- **SqlServer 实跑 14 个 JsonColumn 用例 → 3 失败**(SqlServer 测试项目 net10.0, 引用共享 LightORMTest, 可连 LocalDB):
  1. `NestedPath_Update` → 双重编码(同 SQLite 症状)
  2. `ScalarAndIndexPath_Set_Update` → `Cannot get the value of a token type 'String' as a number`(数字被写成字符串)
  3. `WholeColumn_Update` → `Unsupported JSON path found in argument 2 of JSON_MODIFY` —— **独立 bug**: SqlServer 的 `HandleJsonColumn` 缺"无索引→整列"分支, `Set(j => j.Data, obj)` 生成 `JSON_MODIFY(col,'$',@p)`, 而 `$` 不是可 MODIFY 的路径(PG/Sqlite 已有 else 分支 → `col = @p`)。
- 结论: SqlServer 需要「标量传**原生值** + 复合走 `JSON_QUERY(@p)`」, 而二者只能在**生成期**区分 → 需框架层配合(值转换钩子/方言标记), **不能只改 provider**。已给出方案待用户选择。

## 方案 A 落地: json 参数改传原始 CLR 值, 序列化下沉到方言 binder (用户选 A)

**设计**: 框架(Builder/批量收集)不再预先序列化 json 列参数, 以 `DbParameterValue(col, 原始值)` 入参; 序列化 + 驱动类型化下沉到 `IDatabaseParameterBinder`。

改动清单:
1. **新增** `src/LightORM/Utils/JsonParameterHelper.cs` (public): `Serialize(object?)` → `ExpressionSqlOptions.Instance.Value.GetJsonHandler().Serialize(...)`; `IsCompositeJsonValue(Type|object)` — 标量白名单 string/char/数值/Guid/DateTime(-Offset)/TimeSpan/byte[]/Uri/Version/object, 其余视为复合。
2. `CustomDatabaseAdapter` 声明实现 `IDatabaseParameterBinder` + `public virtual bool BindParameter(...)`: json 列 → `DbType.String` + `Serialize(value)`。**所有 provider 继承即得默认 json 能力**。
3. 框架移除预序列化: `InsertBuilder`(json 分支整体删掉, 与普通列同路), `UpdateBuilder`(UpdateSpecific 后处理 + 整列分支的 Serialize 都删), `BatchSqlInfoExtensions.ToDictionaryParameters`(直接 `col.Value`)。
4. PG/KingbaseES: `BindParameter` 改 `override`, json 条件从 `column.IsJsonColumn && value is string` 改为只看列; 值 null 传 null; 去掉类声明上冗余的 `IDatabaseParameterBinder`。
5. SqlServer: 新增 `override BindParameter` — 复合值序列化+String(return true), **标量 return false** 交框架兜底传原生值; `HandleJsonColumn` 路径更新第三参数按 `IsCompositeLeaf(leafMember)`(路径末端成员类型) 决定 `JSON_QUERY(@p)` / `@p`。
6. MySQL: `JSON_SET` 第三参数包 `CAST(?p AS JSON)`(无实库)。SQLite/Oracle/Dameng 走默认 binder(SQLite `JSON(@p)` 不变; Oracle/Dameng 行为同改动前)。

**关键约束/坑**:
- **表达式缓存**: `Resolve` 的 cache key 只有 `(SqlAction, Hash, Depth)`, 不含值 → SQL 侧的"形状分支"必须由**表达式结构**(成员类型)决定, 不能用运行时值。所以 SqlServer SQL 侧看成员类型、binder 看值类型; 二者在 `object`/接口等无法判定时**统一按标量**(最安全)。
- 绑定阶段的 adapter 是 `Provider.DatabaseAdapter`(真 adapter), 不是 `ScopedDatabaseAdapter` → `adapter is IDatabaseParameterBinder` 成立, 无需给 Scoped 加转发。
- json 列参数以前是"框架序列化 + 无 binder(兜底 DbType.String)", 现在是"binder 接管序列化 + DbType.String" — 对未覆盖 binder 的方言行为等价。

**验证**:
- Sqlite `JsonColumn*` **16/16**; SqlServer(LocalDB 2019) `JsonColumn*` **16/16**(此前 3 失败: NestedPath 双编码 / Scalar 数字变字符串 / WholeColumn 非法 `$` 路径 —— 全部转绿)。
- Sqlite 全量: 162 用例 / 145 通过 / 17 失败 —— **与改动前数字完全一致**; 17 个失败逐条为既有问题(SelectWithAttr、InsertRange、Navigate Where、ArrayAccess_List、RowNumber、Repository_*、ROLLUP/CUBE 3 个、临时表 2 个、事务 2 个、FullDelete、TestSelectOneTable), **无 json 相关**。
- 编译: core 全 TFM + 7 个 provider 库(PostgreSQL/KingbaseES/Sqlite/SqlServer/MySql/Oracle/Dameng) + Sqlite/SqlServer/PG 测试项目 全 0 错误。
- PG 生成 SQL 实测: `JSON_DATA = JSONB_SET(JSON_DATA::JSONB,'{NestJson,Name}',@Json::JSONB)`(参数显示原始值 `test`)、`UpdateColumns` → `JSON_DATA = @Json`、批量 → `SET JSON_DATA = CASE WHEN ID=@Id_0 THEN @Json_0 ... END`。

**新增用例**: `ExecutionTest.JsonColumnCases.cs` → `JsonColumn_CompositePath_Set_Update`(Id=101, `Set(j => j.Data!.NestJson, new JsonData{Name="CompositeNest",Value=77})`) —— 唯一能验证 SqlServer `JSON_QUERY` 分支的用例。

## 达梦（Dameng）json 列处理 — 实测与修复

**本机有可用 DM8 实例**：`localhost:5236`（`LIGHTORM_TEST/LIGHTORM_TEST/DAMENG`），`LightORMTest.Dameng` 可直接实跑。

**探针结论（DmProvider 直连 DM8 实测）**：
- `JSON_SET(col, path, value)` 按**第三参数的 SQL 类型**决定 JSON 值：varchar 原样作 JSON 字符串（不解析，故 `'"abc"'` → `{"a":"\"abc\""}` 双重编码）、number → JSON 数字、NULL → JSON null。
- `JSON_VALUE(col, '$.a')` 读取正常；`JSON_QUERY` **函数不存在**（"无法解析的成员访问表达式"）。
- **`CAST(x AS JSON)` 可用**，且 `JSON_SET(col,path,CAST(:p AS JSON))` 对 **字符串/对象/数组/数字/布尔/null 全部正确** —— 一行解决，**无需**像 SqlServer 那样按标量/复合分流。
- 列类型 `JSON` / `CLOB` / `TEXT` 三种行为一致；整列赋值 `col = :p`（文本存储、读取反序列化）正常；整列置 NULL 正常。
- Where 路径比较 `JSON_VALUE(DATA,'$.Name') = :p` 正常（参数无列元数据 → 不序列化）。
- `JSONBackend.Binary` 在本机 DM8 **不可用**：`JSONB_VALUE` 不存在、`JSONB_SET` 报"JSON路径表达式语法错误" → 用默认 `JSONBackend.Text`。

**改动（2 处，仅达梦）**：
1. `CustomDamengAdapter.HandleJsonColumn` 路径更新分支第三参数 → `CAST(:p AS JSON)`（替换原先直接拼 `:p`）；删掉遗留的注释块与未使用的 `IsCompositeLeaf`。
2. 删除 `CustomDamengAdapter.BindParameter` 覆写（原为"仅复合值序列化、标量 return false"），改用 `CustomDatabaseAdapter` 默认 json 绑定（统一序列化 + `DbType.String`）—— 因为 CAST 方案要求参数**始终**是合法 JSON 文本。同时清理 `using System.Data/System.Reflection/LightORM.Utils`。

**验证**：达梦 `~JsonColumn` **32/32 通过**（16 用例 × 2 测试类，覆盖字符串/复合对象/数组索引路径 Set、整列 Set、UpdateColumns、批量、SqlFn.JsonSet）。生成 SQL 实测：
- `UPDATE "JSON_EXEC_TEST" SET "DATA" = JSON_SET("DATA",'$.NestJson.Name',CAST(:Data AS JSON)) WHERE ("ID" = 101)`
- `"ARR" = JSON_SET("ARR",'$[1].Name',CAST(:Arr AS JSON))`
- 整列：`"DATA" = :Data, "LST" = :Lst, "OBJ" = :Obj`

**环境坑**：达梦跑较大测试集时 `InitDatas` 建连报 `DmException 6001 ... 每个套接字地址(协议/网络地址/端口)只允许使用一次`，大量用例因此"失败"——是连接数/socket 环境问题，非代码 bug；隔几秒重跑即恢复（`~JsonColumn` 复跑 32/32 通过）。

**补测**：新增 `test/LightORMTest.Dameng/SqlGenerate/InsertSql_Json.cs`、`UpdateSql_Json.cs`（一行子类，与 PG/SqlServer 同形），达梦 SQL 生成 7 用例全通过。生成 SQL 实测 `"JSON_DATA" = JSON_SET("JSON_DATA",'$.NestJson.Name',CAST(:Json AS JSON))`。

## MySQL json 列处理 — 实跑验证与修复（用户: MySQL 本地库已启动，处理 MySQL；Oracle 跳过）
