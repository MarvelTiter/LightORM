## 抽取方言能力档案基类 `DbCapabilities<TDatabase, TFeatures>`

用户提出：三个方言的 `XxxCapabilities` 重复代码很多，想抽基类，但 **net462 不支持接口中的静态抽象方法**
（`static abstract` 需要 .NET 7+ 运行时），导致 `Start` / `PrepareProbeConnectString` 没法抽。

### 落地（`src/LightORM/Implements/DbCapabilities.cs`）
基类提供：`Baseline` / `ForVersion(Version)` / `Start(factory, cs, specificVersion, detectVersion)`
+ `ServerVersion` / `Version` / `Source` / `IsResolved` / `Features` / `Override` / `OpenBeforeRead`。
方言只实现三样（**都是实例成员**）：
- `protected abstract string ProbeTarget`（= `DbBaseType.Xxx.Name`，探测单飞键）
- `protected abstract string? PrepareProbeConnectString(cs, seconds)`
- `public abstract TFeatures MapFeatures(Version?)`

### 关键手法（net462 下把静态工厂抽到基类）
`where TDatabase : DbCapabilities<TDatabase, TDatabaseFeatures>, new()`，静态工厂里
`var metadata = new TDatabase();` —— 借这个**空实例**读出方言元数据（探测键 / 委托 / OpenBeforeRead），
`DbVersionProbe.Start(...)` 拿到结果后再写回同一实例返回。空实例只是元数据载体，成本可忽略。
- 泛型基类内通过类型参数访问 `protected` 成员（CRTP）在 net462 下合法，未踩限制。
- `Probe` 从 `public required` 改为 `protected { get; set; } = DbVersionProbe.None;`（不再需要
  `required`，用户之前加的 `RequiredMemberAttribute` 等 polyfill 可留作它用）。
- 三个方言类现在各约 60~80 行（只剩枚举 + 三个 override）。
- 用户原稿里的 `Create(DbVersionProbe)` + object initializer（`required Probe`）不可用：`new TDatabase()`
  需要 `new()` 约束，且方言私有构造会让约束无法满足 → 改为基类私有 `ForProbe(instance, probe)`。

### 验证
- 编译：三个 provider **全部 TFM（含 net462、netstandard2.0）** 0 错误；三个测试项目 0 错误。
- 行为：SqlServer `Select_Paging_Test` 1/1 通过；MySQL `Group_Rollup*` 3/3 通过 ⇒ 探测 → 能力位链路未变。

### 基类拆成两层（`src/LightORM/Implements/DbCapabilities.cs`）
- `DbCapabilities<TDatabase>`：探测机制 + `ServerVersion`/`Version`/`Source`/`Baseline`/`ForVersion`/`Start`/`Override`；
  `ProbeTarget` 抽象，`PrepareProbeConnectString` / `OpenBeforeRead` 改**虚成员给默认值**（前者返回 null）。
- `DbCapabilities<TDatabase, TDatabaseFeatures> : DbCapabilities<TDatabase>`：只加 `MapFeatures` + `Features`。
- 理由：没有能力位的方言（PG/KES/Dameng）不该被硬塞一个空枚举。

### 四方言档案
- `PostgreSQLCapabilities` / `KingbaseESCapabilities` / `DamengCapabilities`：**无能力位**（实测其 SQL 生成本就
  没有按版本二选一的分支），只承载版本探测供诊断，并让 `SpecificVersion` / `DetectVersion` 语义一致。
- `SqliteCapabilities`：`SqliteFeatures.Jsonb`（3.45+）+ `OpenBeforeRead => false`。
  `UseBinaryJson(JSONBackend)` = 用户选了 Binary **且**服务端支持 ⇒ 老库自动降级到 `json_*`。
  **AI 基线取 `Full`**（与 SqlServer 同为乐观）：否则 `DetectVersion=false` 的 ToSql 场景会生成出与今天不同的 SQL。
- 接线点：七个 provider 构造期 `Capabilities = XxxCapabilities.Start(factory, MasterConnectionString, generate.SpecificVersion, generate.DetectVersion)`，
  并把 `Capabilities` 作为公开属性暴露；SQLite 另把 capabilities 传进 `SqliteTableHandler` / `SqliteMethodResolver` / `CustomSqliteAdapter`。

## 实现 SQLite 反向读表结构（`SqliteTableHandler` 三个 `NotImplementedException`）

需求：`GetTablesSql()` / `GetTableStructSql(string table)` / `ParseDataType(ReadedTableColumn, out string)`。

### 实现（`src/Providers/LightORM.Providers.Sqlite/SqliteTableHandler.cs`）
- **列表**：`SELECT name AS TableName FROM sqlite_master WHERE type='table' AND name NOT LIKE 'sqlite\_%' ESCAPE '\' ORDER BY name`。
  `sqlite_%` 是引擎自己的表（`sqlite_sequence` 等），必须排掉。SQLite 无 schema 概念，`ReadedTable.SchemaName` 留空。
- **结构**：走**表值函数 `pragma_table_info('t')`**，**不是** `PRAGMA table_info(t)` 命令 —— 后者不能出现在
  SELECT/子查询里，而"是不是 rowid 别名"必须**数同表主键列个数**（只有单列 INTEGER 主键才是别名），
  需要自连接。SQL：`CASE WHEN ti.pk>0 AND upper(trim(ti.type))='INTEGER' AND (SELECT COUNT(*) FROM pragma_table_info('t') p WHERE p.pk>0)=1 THEN 'YES' ELSE 'NO' END`。
  - `Nullable`：`notnull=1 OR pk>0` → `'NO'`（主键在 SQLite 里隐式 NOT NULL）。
  - `Comments` 恒 `''`（SQLite 无列注释）；`DefaultValue` 取 `COALESCE(dflt_value,'')`；
    `Length` = `instr(type,'(')>0` 时取括号内（`replace(substr(...), ')', '')`），否则空串。
  - 表名要进**字符串字面量** ⇒ `EscapeLiteral` = `Replace("'", "''")`。
- **类型映射**：先剥掉 `(len)` 再 `Trim().ToUpperInvariant()` 走精确 `switch`（TINYINT/SMALLINT|INT2/INT|INTEGER|INT4/BIGINT|INT8/
  UNSIGNED BIG INT/BOOLEAN/REAL|DOUBLE/DOUBLE PRECISION/FLOAT/NUMERIC|DECIMAL/TEXT|CLOB|CHAR...|JSON/DATE/DATETIME/TIMESTAMP/
  TIME/BLOB|BINARY|VARBINARY/UUID|GUID|UNIQUEIDENTIFIER）；未命中按 **SQLite 官方亲和性顺序**兜底
  （`INT` → `CHAR|CLOB|TEXT` → `BLOB` → `REAL|FLOA|DOUB`），最后 `object?` + `return false`。
  - 可空修饰来自 `column.Nullable`（`YES/Y/TRUE/1`）；`byte[]` 不带 `?`（引用类型不加空标注）。

### 踩坑
- **net462 无 `System.Range`/`System.Index`**：`declared[..paren]` 编译报 CS0518 ⇒ 改 `declared.Substring(0, paren)`。
- **测试断言写错两次**（不是实现错）：
  1. 以为 LightORM 写出的 `string` 列带 `NOT NULL` ⇒ 实际 `Nullable='YES'`（`SqliteTableHandler.Writer` 对非主键字符串不写 NOT NULL）；
  2. `FLOATING POINT` 直觉该是浮点，实际按官方顺序 `POINT` 含 `INT` 先被整数族截胡 ⇒ **`int` 才是正确结果**，
     这条已回写成断言 + 代码注释，防止后人"优化"成浮点分支。
- 表名带单引号的用例最初写成 `DROP TABLE "ZZ_QU''OTE"` —— `''` 只是**单引号字符串**里的转义，双引号标识符里直接写 `'` 即可。

## 补上达梦反向读表结构（`DamengTableHandler` 三个 `NotImplementedException`）

### 先用四轮探针把达梦的元数据摸干净（临时 MSTest + `DmConnection` 直连，跑完删除）

**第一轮**建表直接失败，报错定位在语句结尾、看不出哪列 —— 逐列重试才发现
**`BOOLEAN`（"无效的数据类型"）和 `UUID`（"非法的基类名"）在达梦不能建列**。其余 40 种类型名全部支持。
教训：建表失败先**逐个类型单独建表**定位，别在一张大表里猜。

**第二轮**（全类型表 + 元数据）
- `USER_TAB_COLUMNS` **可用**，但**没有 `IDENTITY_COLUMN` 列**（报"无效的列名"），
  而且 IDENTITY 列的 `DATA_DEFAULT` 也是空的 ⇒ Oracle 那套判自增的路子走不通。
- 列注释在 `USER_COL_COMMENTS`（未注释列给空串）；主键在 `USER_CONSTRAINTS`/`USER_CONS_COLUMNS` ✓
- 最后靠 `SYSOBJECTS`(TYPE$='SCHOBJ', SUBTYPE$='UTAB') 找到表 ID → `SYSCOLUMNS`，
  发现 **`INFO2` 的 bit0 就是自增标记**（IDENTITY 列=1，普通列=0）。
- `DATA_SCALE` 并不是纯小数位：`JSON/JSONB=16384`、`NVARCHAR2/NVARCHAR=7`、`NCHAR=8`、`TIMESTAMP=6`。
  ⇒ 数值分支必须再用 `TYPE$ IN ('DECIMAL','NUMERIC','NUMBER','DEC')` 限定。

**第三轮**（关键的两个坑）
1. **`USER_TAB_COLUMNS.DATA_LENGTH` 对 `NVARCHAR2` 给的是字节数**：`NVARCHAR2(64)` → 128，且 `CHAR_LENGTH` 为 0
   （而 `NVARCHAR(64)` → CHAR_LENGTH=64，`NCHAR(10)` → 10）。
   **`SYSCOLUMNS.LENGTH$` 才是字符数**（给 64）⇒ Length 全改用 `s.LENGTH$`。
   这条直接决定了 LightORM 默认 `UseUnicodeString=true` 建的表（NVARCHAR2）能不能读对长度。
2. **JSON / JSONB 物理存成 `BLOB`**（`DATA_TYPE='BLOB'`），与真 BLOB 无法靠类型名区分。

**第四轮**（收口 JSON）
- 发现达梦有官方视图 **`USER_JSON_COLUMNS(TABLE_NAME, COLUMN_NAME, FORMAT, DATA_TYPE)`**，
  实测 3 个 JSON 列全被收录、普通 BLOB 不在其中。
- 但最终**没采用它**：改用 `SYSCOLUMNS.SCALE = 16384`（达梦给 JSON 的 BLOB 打的内部子类型标记，普通 BLOB=0；
  达梦十进制标度最大 38，不可能自然取到 16384）。理由是失败模式更温和 ——
  视图不存在会让**整条 SQL 报错、功能全废**，而 16384 失效最多是 JSON 列被当 `byte[]`。
- 同一轮把**最终 SQL 原样预演**通过，Length/Nullable/PK/Identity/Comments/默认值一次性全对。

### 实现（`src/Providers/LightORM.Providers.Dameng/DamengTableHandler.cs`）
- 列表：`SELECT TABLE_NAME AS TableName FROM USER_TABLES ORDER BY TABLE_NAME`。
- 结构：`USER_TAB_COLUMNS` 主表 + `USER_COL_COMMENTS` / `USER_CONS_COLUMNS`+`USER_CONSTRAINTS` /
  `SYSOBJECTS`+`SYSCOLUMNS` 四个 `LEFT JOIN`（挂不上只降级，不丢列）。
- `DataType`：`CASE WHEN DATA_TYPE='BLOB' AND s.SCALE=16384 THEN 'JSON' ELSE DATA_TYPE END`。
- `Length`：LOB 类 → `''`；数值类 → `"精度,标度"`；其余 `s.LENGTH$ > 0` 才给值，否则 `''`。
- `ParseDataType`：达梦 `DATA_TYPE` 是**纯类型名**（无括号），定点细分只能靠 `column.Length`；
  `NumericType` 带逗号 → decimal，无精度信息 → **decimal**（裸 `NUMBER` 是浮点语义）；
  `FLOAT → double`（达梦 FLOAT 是 8 字节双精度）、`REAL → float`；`BIT → bool`；`JSON/JSONB → string`。
- 与 writer 的不对称是刻意的，注释里写明了：`bool` 写 `CHAR(1)`、`Guid` 写 `CHAR(36)`，
  读回一律 `string`（真 `CHAR(1)` 多存 `'Y'`/`'N'`，猜 bool 会反序列化失败）—— 口径与 SQLite 一致：**不逆向猜测 writer 的私有约定**。
