## 剩余方言 json 列处理检查（PostgreSQL / KingbaseES / Oracle）

### 结论
6 个方言（PG / Kingbase / MySQL / SqlServer / Sqlite / Dameng）json 链路已闭环；**Oracle 是唯一有缺口的**。
PG 与 Oracle 的 SqlGenerate json 用例（每方言 7 个，不连库）全部通过；**KingbaseES 没有测试项目**，无法覆盖。

### Oracle 缺口（3 处，均需 21c+ 实库验证）
1. `CustomOracleAdapter.HandleJsonColumn` 缺 `HasIndexInfo()` 整列分支 → `Set(j => j.Json, obj)` 生成
   `JSON_TRANSFORM(col, SET '$' = :p)`；JSON 函数对 NULL 输入返回 NULL → 整列写回静默丢失（与已修的 MySQL bug 同类）。
2. 路径更新的值参数未按 JSON 解析：Oracle 的 `SET '$.a' = :p`（:p 为 SQL 字符串）会作为 **JSON 字符串**写入，
   于是框架下发的"序列化 JSON 文本"被双重编码（与 Dameng 同类）→ 应改为 `SET '$.a' = JSON(:p)`。
3. 无 `IDatabaseParameterBinder` 覆写 → 参数按 VARCHAR2 下发，长 JSON 可能超 4000/8192 限制（宜绑 CLOB）。

### Oracle 版本门槛（已查证）
- 原生 `JSON` 数据类型与 `JSON_TRANSFORM` 均为 **Oracle 21c 引入**；12c/19c 没有任何 JSON 变更函数。
- `TableOptions.JSONBackend` 默认 `Text` → Oracle 建表输出 `JSON` 类型，≤19c 直接失败（这是"Oracle 库不支持 json 列"的根因）。
- 绕过手段：`OracleTableOptions.SpecificJsonColumnDbType` 设为 `CLOB`/`VARCHAR2(n)`，应用中按 JSON 文本读写（无路径更新能力）。

### 附带发现
- `JsonColumnContext.HasIndexInfo()` 的 `|| Members.Any(i => i.IndexValue.HasValue)` 是死代码（`Members.Count > 0` 已覆盖）。
- PG/Kingbase 整列 Set 分支保留 `@p::JSONB`（binder 已声明 jsonb，恒等 cast，可清理）；`UpdateColumns`/批量路径为 `col = @p`，无冗余 cast。
- 调试输出不一致：`ToSqlWithParameters` 的"参数列表"显示 json 列**原始 CLR 值**，批量行数据显示**序列化文本**。

### 无实库时的验证手段（有效）
`SqlGenerate` 目录用例只打印 SQL 不连库，任何方言都能跑：
`dotnet test <provider 测试项目> -f net10.0 --filter "FullyQualifiedName~SqlGenerate.InsertSql_Json|FullyQualifiedName~SqlGenerate.UpdateSql_Json" --logger "console;verbosity=detailed"`。

## ExpressionResolver 架构通读（纯分析，未改代码）

`src/LightORM/Utils/ExpressionResolver.cs`（695 行）三部分：`SelectMap` record struct、`ExpressionExtensions`（缓存入口 `Resolve` + 两个 `OperatorParser` 重载）、`ExpressionResolver` 类（IExpressionResolver 实现）。

调用链：`SqlBuilder.ResolveExpressions` → `Expression.Resolve(options, ctx)`（cache key = `(SqlAction, Hash64, Depth)`，命中且 `NeedToExtractValues` 时只经 `ExpressionValueExtract` 重算值）→ 未命中 `ExpressionResolverPool.Rent` → `Visit(expression)` → `ExpressionResolvedResult` 快照（`ReplaceConstantValue` 把 NULL 常量占位符改写为 `IS NULL`/`IS NOT NULL`/`NULL`）→ `HandleResult` 分派到 Where/SelectValue/Join/GroupBy/OrderBy/Having → `HandleSqlParameters` 把占位符替换为参数引用并填入 `DbParameters`。

关键机制备忘：
- `Visit` 是 `VisitX(...)` 结果再 `Visit(...)` 的两段式（让 VisitX 可"返回下一个要访问的节点"），这是 `VisitMember` 返回 `exp.Expression`、`VisitUnary` 返回 Operand 的原因；`VisitMethodCall` 的 `op_Implicit` 直接返回 `Arguments[0]`。
- 成员栈 `Members : Stack<MemberPathInfo>` 承担全部"中间成员"，遇到 Parameter 基底的列时统一 `Members.Clear()` 收口。
- `VisitMember` 的 Parameter 基底分支四路：Navigate → JsonColumn → Aggregated → 普通列（都是 return null + 已写 SQL）。
- `VisitConstant` 双路径：`Members.Count > 0` → 参数化（`{ParameterPrefix}{成员名_连接}` 写进 Sql + `DbParameters`，`ContainVariable=true`）；否则按常量内联（null→随机 8 位名 + `ConstantNull` 延后替换为 IS NULL；数字直出；bool→`HandleBooleanValue`，`IsNot` 时取反；DateTime→`HandleDateValue`；**其他一律 `'` 包裹且不做转义**，含单引号的字符串会生成错误 SQL）。
- `VisitMember`/`VisitParameter` 内 `GetColumn(name)!`、`GetTable(paramExp!)` 为 `!` 强解引用；`RequiredTableAlias` 仅 Select + 特定 partial 为 true。
- 隐患清单（同 2026-09-14 前段）：`ConstraintValue` 未转义、`HasIndexInfo` 冗余、PG 整列分支重复 cast。
